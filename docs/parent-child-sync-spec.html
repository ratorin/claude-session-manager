1. 背景と課題

1.1 旧方式の問題（v1.x）

v1.x では、エージェント間の親子関係は session-manager.json の parentAgent フィールドで管理し、セッションIDで紐づけていた。しかし以下の問題が顕在化した:

v1.x の構造的問題
  • セッションIDが無効になるとエージェントの紐づけが切れる（IDベースの脆弱性）
  • セッション肥大化で --resume が不安定になる
  • session-manager.json と個別ルールファイルの二重管理でデータが不整合になりやすい
  • CSM:CHILDREN タグの注入は CSM 独自実装であり、CLI本体の仕組みと噛み合わない
  • 親エージェントは配下の子エージェント情報をルールファイルから知ることができず、タスク委任ができない

1.2 CLIの進化による転機

2026年4月のClaude Code CLI大幅アップデートにより、エージェント管理の標準機能が追加された:

CLI新機能 概要 CSMへの影響
~/.claude/agents/*.md エージェント定義ファイル（CLI標準） session-manager.json の agents[] が不要に
claude --agent <name> 名前でエージェント起動 --resume + セッションID が不要に
memory: project セッション跨ぎの記憶保持 ルールファイルへの状態書き込みが不要に
permissionMode 権限を宣言的に管理 手動の権限設定が不要に
claude agents list CLI標準のエージェント一覧 session-manager.json のスキャンが不要に

3. エージェント定義ファイル v2.0 新規

3.1 標準フォーマット

~/.claude/agents/*.md は YAML frontmatter + Markdown 本文で構成される。frontmatter がメタデータ、本文がシステムプロンプトとなる。

---
name: csm-dev                   # CLI識別子（英数字必須。日本語は agents list に表示されない）
description: CSM開発を担当        # Agent ツール表示用の説明
model: sonnet                    # opus / sonnet / haiku / claude-sonnet-4-6[1m] / claude-opus-4-6[1m] / inherit
memory: project                  # セッション跨ぎ記憶（user / project / local）
tools: ["Read", "Edit", "Write", "Bash", "Grep", "Glob", "Agent"]
permissionMode: acceptEdits      # default / acceptEdits / plan / auto / dontAsk
parentAgent: director            # 組織階層（CSM独自フィールド）
status: active                   # 稼働状態（CSM独自フィールド）
workDir: c:/xampp/Project/csm    # 作業ディレクトリ（CSM独自フィールド）
---

あなたはCSM開発部です。
（ここにシステムプロンプト = ルール本文）

3.2 フィールド一覧

フィールド 必須 値 説明
name はい 英数字+ハイフン CLI識別子。日本語は agents list に表示されないため非推奨
description はい テキスト Agent ツール選択画面で表示される説明
model いいえ opus / sonnet / haiku / claude-sonnet-4-6[1m] / claude-opus-4-6[1m] / inherit 省略時は親から継承。--agent 単体では無視される場合があり、--model 明示が確実。
⚠️ 1Mモデルは必ずフルID（claude-sonnet-4-6[1m]）で指定。短縮形 sonnet[1m] は旧バージョン(4.5)になる。
inherit は呼び出し元のモデルを継承（ビルトインエージェントで使用）
memory いいえ user / project / local セッション跨ぎの記憶保持。CLI起動（--agent）のみ有効、Agent ツール経由では無効
tools いいえ 配列 利用可能ツール制限。省略時は全ツール。Bash(git *) で実行範囲を制限可能
permissionMode いいえ default / acceptEdits / plan / auto / dontAsk 権限を宣言的に管理。plan = 読み取り専用
parentAgent いいえ エージェント名 / none CSM独自フィールド。組織階層の定義。CSMはこの値を読み取り組織図を構築
status いいえ active / idle CSM独自フィールド。稼働状態
workDir いいえ パス CSM独自フィールド。作業ディレクトリ

3.3 配置場所とスコープ

場所 スコープ 用途
~/.claude/agents/ 全プロジェクト共通（グローバル） 組織全体で共有するエージェント
.claude/agents/ プロジェクト固有（ローカル） 特定プロジェクト専用のエージェント

3.4 memory: project の動作

重要: memory: project はCLI起動時のみ有効
  • claude --agent <name> -p で起動 → 記憶が保存・読み込みされる
  • Agent ツール（subagent_type）経由 → 記憶は保存されない（親セッション内の一時的な実行）
  • 記憶は ~/.claude/projects/{path}/memory/ に自動保存される
  • MEMORY.md がインデックス、個別ファイルに記憶本体が格納される
  • ⚠️ enablePersistentMemory は旧フィールド名（v2.1.100以降で認識されない）。正式名は memory

4. 起動方式と制限事項 v2.0 新規

4.1 起動コマンド

# 部署に指示を投げる（標準）
echo "指示内容" | claude --agent csm-dev -p > c:/xampp/.agent-rules/tmp/agent_csm-dev_{タスク}.txt 2>&1

# 同じ部署に並行タスク（別プロセスとして起動）
echo "タスクA" | claude --agent csm-dev -p > c:/xampp/.agent-rules/tmp/agent_csm-dev_taskA.txt 2>&1 &
echo "タスクB" | claude --agent csm-dev -p > c:/xampp/.agent-rules/tmp/agent_csm-dev_taskB.txt 2>&1 &

4.2 起動方式の比較

方式 記憶保持 履歴保存 CSM検知 推奨用途
claude --agent <name> -p ○ ○ ○ 部署への指示（本命）
Agent ツール（subagent_type） ✗ ✗ ✗ 使い捨て調査のみ
--resume <セッションID> ○ ○ ○ DEPRECATED

4.3 禁止事項

以下は明確に禁止:
  • claude -p 単体（--agent なし） — ルール・メモリが適用されず、意図しない動作をする
  • --continue — 最新セッションを再開するため、別エージェントのセッションが割り込む。エージェント単位ではなくグローバルに最新のセッションを拾ってしまう
  • Agent ツールでの並行タスク — 親コンテキストの94%を占有した実例あり。トランスクリプト漏洩バグ（Issue #14118、OPEN）も存在するため、並行タスクには必ずCLI起動を使う

4.4 Agent ツール（subagent_type）の制限事項

Agent ツールで「できること」と「できないこと」
項目 Agent ツール CLI起動
エージェント定義（ルール）の適用 ○ ○
モデル指定の反映 ○ △（--model 明示が確実）
memory: project の記憶保持 ✗ ○
独立したセッション履歴 ✗ ○
CSMによる稼働検知 ✗ ○
並行実行の安全性 ✗（コンテキスト占有） ○（別プロセス）

結論: Agent ツールは「名前でエージェントを呼んで即答を得る」使い捨て調査に限定。永続的なタスク実行はCLI起動一択。

5. 同期設計概要

5.1 新方式の同期コンセプト

CSMは agents/*.md の parentAgent フィールドを読み取り、子を持つ親エージェントのルール本文に配下一覧と /dispatch コマンドの使用法を自動注入する。

旧方式 vs 新方式の同期
項目 旧方式 新方式
データソース session-manager.json agents/*.md の frontmatter
注入先 個別ルールファイル（.agent-rules/配下） agents/*.md の本文
注入内容 CSM:CHILDREN タグ（テーブルのみ） 配下一覧テーブル + /dispatch の使い方 + 起動コマンド例
マーカー <!-- CSM:CHILDREN:START/END --> <!-- CSM:CHILDREN:START/END -->（形式は同一、注入内容を拡張）

5.2 方針: マーカーセクション方式（継続）

v1.x から引き続き、親の agents/*.md 本文にHTMLコメントマーカーで囲んだ自動管理セクションを設ける。マーカー内のみCSMが自動更新し、マーカー外は一切触れない。

設計判断: なぜフロントマターではなく本文か？
  • フロントマターの description はClaude Codeのsystem promptに注入される重要な領域。肥大化を避ける
  • 本文はユーザーが自由にカスタマイズできる領域であり、マーカーで区切ることでCSM管理部分と共存できる
  • agents/*.md の本文全体がシステムプロンプトになるため、子エージェント情報をここに入れることでClaude Codeが自然に認識する

8. 同期ロジック詳細

8.1 全体フロー（v2.0）

エージェント操作（追加/編集/削除） │ ▼ agentFileManager.createAgent() / updateAgent() / deleteAgent() │ agents/*.md を直接読み書き ▼ parentChildSync.syncParentAgentFile(parentName) │ ├── 1. parentName の agents/*.md を読み込み │ agentFileManager.readAgent(parentName) │ ├── 2. 全 agents/*.md をスキャンして子一覧を取得 │ agents.filter(a => a.frontmatter.parentAgent === parentName) │ ├── 3. CHILDRENセクションを生成（テーブル + /dispatch 使用法） │ buildChildrenSection(children) │ ├── 4. マーカー破損チェック │ validateMarkers(content) → 'valid' | 'corrupted' | 'absent' │ ├── 5. マーカー状態で分岐 │ ├── valid → マーカー間を置換 │ ├── absent → 本文末尾に追加 │ └── corrupted → 変更せず警告出力 │ └── 6. agents/*.md に書き戻し agentFileManager.writeAgentBody(parentName, newContent)

8.2 セクション生成ロジック（v2.0）

function escapeTableCell(value: string): string {
    return value.replace(/\|/g, '\\|').replace(/\n/g, ' ');
}

function buildChildrenSection(children: AgentConfig[]): string {
    if (children.length === 0) return '';

    const header = '<!-- CSM:CHILDREN:START -->\n## 配下エージェント\n';
    const tableHeader = '| 部署名 | モデル | 役割 | 権限モード |\n|--------|--------|------|----------|\n';

    const rows = children
        .sort((a, b) => a.name.localeCompare(b.name, 'ja'))
        .map(c => {
            const name = escapeTableCell(c.name);
            const model = escapeTableCell(c.model || 'sonnet');
            const role = escapeTableCell(c.description || '未設定');
            const perm = escapeTableCell(c.permissionMode || 'default');
            return `| ${name} | ${model} | ${role} | ${perm} |`;
        })
        .join('\n');

    // v2.0追加: /dispatch の使い方と手動コマンド例
    const dispatchGuide = `

### 子エージェントの呼び出し方

\`/dispatch\` スキルを使う:
\`\`\`
${children.map(c => `/dispatch ${c.name} "指示内容"`).join('\n')}
\`\`\`

手動で投げる場合:
\`\`\`bash
echo "指示内容" | claude --agent <name> -p > c:/xampp/.agent-rules/tmp/agent_{name}_{タスク}.txt 2>&1
\`\`\``;

    const footer = '\n<!-- CSM:CHILDREN:END -->';

    return header + tableHeader + rows + dispatchGuide + footer;
}

8.3 マーカー検証・置換ロジック

v1.x と同一のロジックを継続使用（マーカー文字列が同じため互換性あり）。

type MarkerState = 'valid' | 'corrupted' | 'absent';

interface ReplaceResult {
    content: string;
    state: MarkerState;
}

function replaceChildrenSection(content: string, newSection: string): ReplaceResult {
    const startMarker = '<!-- CSM:CHILDREN:START -->';
    const endMarker = '<!-- CSM:CHILDREN:END -->';

    const startIdx = content.indexOf(startMarker);
    const endIdx = content.indexOf(endMarker);

    // マーカー破損チェック（片方のみ存在）
    if ((startIdx !== -1) !== (endIdx !== -1)) {
        return { content, state: 'corrupted' };
    }
    // 開始が終了より後ろ（逆順）
    if (startIdx !== -1 && startIdx > endIdx) {
        return { content, state: 'corrupted' };
    }

    if (startIdx !== -1 && endIdx !== -1) {
        const before = content.substring(0, startIdx);
        const after = content.substring(endIdx + endMarker.length);

        if (newSection === '') {
            const trimmedBefore = before.replace(/\n{2,}$/, '\n');
            const trimmedAfter = after.replace(/^\n{2,}/, '\n');
            return { content: trimmedBefore + trimmedAfter, state: 'valid' };
        }
        return { content: before + newSection + after, state: 'valid' };
    }

    if (newSection === '') return { content, state: 'absent' };
    return {
        content: content.trimEnd() + '\n\n' + newSection + '\n',
        state: 'absent'
    };
}

8.4 名前変更時のフロー

■ 子エージェント名前変更 agentFileManager: rename(oldName, newName) → 旧 agents/{oldName}.md を削除 → 新 agents/{newName}.md を作成 → syncParentAgentFile(parentName) // ★1回の同期で旧名行が消え新名行が入る

8.5 呼び出しシーケンス

■ 子エージェント追加 CSM UI: フォーム送信 → agentFileManager.createAgent(config) // agents/{name}.md 作成 → syncParentAgentFile(config.parentAgent) // ★親の本文に注入 ■ 子エージェント削除 CSM UI: 削除ボタン → const parentName = agent.parentAgent // 削除前に親名を保持 → agentFileManager.deleteAgent(agent.name) // agents/{name}.md 削除 → syncParentAgentFile(parentName) // ★親から除去 ■ 子エージェント編集（親変更あり） CSM UI: フォーム保存 → const oldParent = readAgent(name).parentAgent → agentFileManager.updateAgent(newConfig) → if (oldParent && oldParent !== newConfig.parentAgent) { syncParentAgentFile(oldParent) // 旧親更新 ★ } → if (newConfig.parentAgent) { syncParentAgentFile(newConfig.parentAgent) // 新親更新 ★ } ■ 子エージェント編集（親変更なし） CSM UI: フォーム保存 → agentFileManager.updateAgent(newConfig) → if (newConfig.parentAgent) { syncParentAgentFile(newConfig.parentAgent) // ★ }

8.6 クロススコープ親子関係ポリシー

スコープをまたいだ親子関係の扱い

agentFileManager.listAgents() はグローバル（~/.claude/agents/）+ ローカル（.claude/agents/）のマージ済みリストを返す（ローカル優先）。

親のスコープ 子のスコープ 同期可否 理由
グローバル グローバル ○ 同期する 同一スコープ、問題なし
グローバル ローカル ○ 同期する グローバル親の agents/*.md にローカル子の情報を追記
ローカル グローバル ○ 同期する ローカル親の agents/*.md にグローバル子の情報を追記
ローカル ローカル ○ 同期する 同一スコープ、問題なし

方針: スコープに関わらず全て同期する。syncParentAgentFile は子一覧を毎回 listAgents() から取得して全体を再生成する。

9. 循環参照防止

CRITICAL: 循環参照は無限ループやデータ破損を引き起こす可能性がある。エージェント追加・編集時に必ず検証すること。

9.1 検証ロジック

/**
 * 循環参照を検出する。
 * childName を parentName の子として設定する場合に、
 * parentName の祖先チェーンに childName が含まれていないか検証。
 *
 * @returns true = 循環あり（設定不可）, false = 安全（設定可能）
 */
function hasCircularRef(
    childName: string,
    parentName: string,
    agents: AgentConfig[]
): boolean {
    const agentMap = new Map(agents.map(a => [a.name, a]));
    const visited = new Set<string>();
    let current = parentName;

    while (current) {
        if (current === childName) return true;
        if (visited.has(current)) return true;
        visited.add(current);
        const agent = agentMap.get(current);
        current = agent?.parentAgent || '';
    }
    return false;
}

15. マイグレーション

15.1 v1.x → v2.0 への移行

移行ステップ
  1. エージェント定義の移行: session-manager.json の agents[] → ~/.claude/agents/*.md に移行（移行スクリプト: c:/xampp/.agent-rules/temp/migrate_agents.py を使用、実行済み）
  2. 旧 CSM:CHILDREN タグの除去: 旧ルールファイル内の CSM:CHILDREN セクションを削除（agents/*.md に新しい形式で再注入されるため）
  3. session-manager.json の縮小: agents[] を削除し、bookmarks / tags / customNames / notes のみ残す
  4. 一括再生成: claudeManager.syncAllParentAgentFiles コマンドで全親の agents/*.md にCHILDRENセクションを注入

15.2 既存環境への自動マイグレーション

agents/*.md にCHILDRENマーカーが存在しない場合、エージェント操作のたびに自動的にマーカーが追加される（「マーカーなし + 子あり → 末尾に追加」の動作）。特別なマイグレーション処理は不要。

activate()時の自動実行は行わない。 理由: 起動のたびに全 agents/*.md を走査するのはパフォーマンスに影響する。必要時に手動コマンドで実行する。

15.3 手動記述との共存

既に手動で子エージェント情報を書いているユーザーがいる可能性がある。マーカー追加時に既存の手動記述はそのまま残す（マーカー外なので影響しない）。

16. リスクと対策

リスク 深刻度 対策
agents/*.md のカスタム本文を上書き CRITICAL マーカー内のみ操作。マーカー外は一切触れない。破損時は変更しない

CSM独自フィールドがCLI更新で衝突 MEDIUM プレフィックス付与（csm-parentAgent 等）を検討。CLIのchangelogを定期監視
memory: project の挙動が不完全 MEDIUM テスト済みで基本動作は確認。長期運用で監視

排他制御の実装方針

// 親名ごとにロックを管理（同じ親への同時書き込み防止）
const syncLocks = new Map<string, Promise<void>>();

async function syncParentAgentFile(parentName: string): Promise<void> {
    if (!parentName || parentName === 'none') return;

    const prev = syncLocks.get(parentName) || Promise.resolve();
    const current = prev
        .then(() => doSync(parentName))
        .catch((err) => {
            outputChannel.appendLine(
                `[ERROR] ${parentName} の親 agents/*.md 同期に失敗: ${err.message}`
            );
        })
        .finally(() => {
            // 完了後にMapから削除（メモリリーク防止）
            if (syncLocks.get(parentName) === current) {
                syncLocks.delete(parentName);
            }
        });
    syncLocks.set(parentName, current);
    await current;
}
