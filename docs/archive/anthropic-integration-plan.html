1. Agent SDK セッション管理API

公式API

# SDK（Python / TypeScript共通のAPI設計）
list_sessions(directory?, limit?, offset?)  → SDKSessionInfo[]
get_session_info(session_id, directory?)     → SDKSessionInfo
get_session_messages(session_id, directory?) → SessionMessage[]
rename_session(session_id, title)
tag_session(session_id, tag_or_none)
fork_session(session_id) → ForkSessionResult
delete_session(session_id)

CSMの現状

  • セッション管理: JSONL直接読み取り（sessionLoader.ts）+ FileHandle API末尾読み取り
  • セッション編集: CSM独自の dataStore.ts（ブックマーク、タグ、リネーム、メモ）
  • サブエージェント検出: subagentDetector.ts で JSONL パース

判断: 部分採用 — Phase 3

採用する部分:
  • fork_session() — CSMの「セッションを新しくする」を SDK API 経由に置換。現在の JSONL コピー方式より堅牢
  • tag_session() — CSMのタグ機能を SDK 経由に統一（現在は dataStore 独自管理）
  • list_sessions() — セッション一覧取得を SDK API 化（JSONL ディレクトリ走査の置換）
見送る部分:
  • rename_session() — CSM独自の customName は Claude Code の /rename とは別管理。統一すると CSM メタデータが失われる
  • delete_session() — CSMは .trash/ 移動ポリシー。SDK の完全削除は方針と矛盾

実装戦略

  1. 抽象レイヤー導入: sessionBackend.ts インターフェース定義（listSessions, getMessages, forkSession 等）
  2. 現行実装を第1バックエンド: JsonlSessionBackend（既存ロジックをラップ）
  3. SDK実装を第2バックエンド: SdkSessionBackend（Agent SDK TypeScript版を利用）
  4. 設定で切替可能（デフォルト: JSONL直接、オプション: SDK経由）
リスク: Agent SDK TypeScript版は Python版 の6.1K stars に比べまだ安定度が不明。SDK の breaking change に追随するコストがある。
対策: 抽象レイヤーで切替可能にし、SDK不具合時はJSONL直接にフォールバック。SDK import は dynamic import で遅延ロード。

2. Chief of Staff agentパターン

Anthropic公式パターン（claude-cookbooks/claude_agent_sdk/01_The_chief_of_staff_agent）

要素公式CSM取締役差分
役割 サブエージェント委任、タスク調整 部署エージェント管理、タスク振り分け 同一思想。CSMが先に実装していた
サブエージェント定義 .claude/agents/ ディレクトリ .agent-rules/ ディレクトリ パス・フォーマットが異なる
出力スタイル .claude/output-styles/ で定義 未実装 新規取り込み候補
フック PostToolUse で操作追跡・監査 Stop/PostToolUse 使用中（todo-flush, ECC hooks） 追加フック活用可
カスタムコマンド .claude/commands/（→ スキルに統合済み） CSM:AUTOマーカーでルールファイル管理 スキル形式への段階移行を検討

判断: 部分採用 — Phase 2

即座に採用:
  • 出力スタイル定義 — .claude/output-styles/ パターンを取締役ルールファイルに組み込み（報告形式の標準化）
  • 取締役ルールファイルのベストプラクティス反映 — 公式 CLAUDE.md ガイドラインに基づく「含める / 除外する」の整理
段階的に採用:
  • .agent-rules → .claude/agents/ への段階移行 — Phase 2で両方式のサポートを追加後、将来的に公式パスに統一
見送り:
  • .agent-rules を完全廃止して .claude/agents/ に統一 — 既存ユーザーの移行コストが高い。既にフォルダ構造移行中で二重の移行は避ける
リスク: .agent-rules/ と .claude/agents/ の二重パス問題。同名エージェントが両方に存在した場合の優先度が未定義。
対策: CSMの resolveRuleFilePath() に .claude/agents/ のフォールバック先を追加。優先度は .agent-rules/ > .claude/agents/（CSM管理優先）。名前衝突時は警告UI表示。

3. Hooks 24種の活用

公式フック一覧と CSM 活用度

フック現在の利用統合候補優先度
Stop todo-flush.js（実装済み） — —
SessionEnd ECC session-end-marker TODO.md最終保存 — Stopは応答完了時だがSessionEndはセッション本当の終了時。より確実なフラッシュポイント Phase 1
SubagentStart 未使用 子エージェント自動追跡 — CSMのsubagentDetectorを補完。JSONL走査なしで即座に検出 Phase 1
SubagentStop 未使用 子エージェントTODO引き継ぎ — 設計書(todo-integration-spec.html §8)で定義済み。子のTodoWriteを親のTODO.mdにマージ Phase 1
SessionStart(compact) ECC pre-compact TODO.md再注入 — コンパクション後にTODO.mdの未完了タスクをコンテキストに再注入（設計書 §6） Phase 1
TaskCreated 未使用 TaskTracker連携 — CSMのTaskTrackerをフックベースに移行（JSONLポーリング不要化） Phase 2
TaskCompleted 未使用 タスク完了通知 — 同上 Phase 2
FileChanged 未使用 TODO.md外部変更検知 — CSMのFileSystemWatcherを補完 Phase 3
PreCompact ECC pre-compact TODO.md保存 — コンパクション前にTodoWrite→TODO.mdのフラッシュ Phase 1
ConfigChange 未使用 session-manager.json変更の監査ログ 低

判断: 採用 — Phase 1

Phase 1 で追加するフック（4つ）

  1. SubagentStop — csm/subagent-todo-merge.js 新設。子エージェントのTodoWrite結果を親のTODO.mdにマージ
  2. SubagentStart — csm/subagent-register.js 新設。CSMのsubagentDetectorにイベント通知（JSONL走査の即時代替）
  3. SessionStart(compact) — csm/compact-reinject.js 新設。コンパクション後にTODO.md未完了を再注入
  4. PreCompact — 既存 todo-flush.js を PreCompact にも登録（コンパクション前の緊急フラッシュ）
リスク: フック増加によるセッション開始/終了の遅延。各フックは async:true だが、累積すると体感速度に影響。
対策: 全CSMフックは async: true + timeout: 10 で実行。失敗時は stderr ログのみで exit 0（他フックをブロックしない）。

既存設計との整合性

  • todo-flush.js（Stop フック）: そのまま存続。SessionEnd フックに同じスクリプトを二重登録して最終保存を確実化
  • SubagentStop は設計書 §8 の「SubagentStop フック」仕様にそのまま対応。実装時は設計書の仕様を参照
  • ECC hooks との共存: CSM フックは ~/.claude/scripts/csm/ に配置し、ECC の ~/.claude/scripts/hooks/ と分離

（ユーザー自由記述）

実装ステップ

  1. autoGenerateRuleFile() でYAMLフロントマターを先頭に出力
  2. resolveRuleFilePath() でフロントマターからメタデータを解析する parseAgentFrontmatter() 関数追加

  4. フロントマターの tools と AgentConfig の allowedTools を双方向同期
リスク: フロントマターとAgentConfigの不整合（どちらが真実か問題）。
対策: AgentConfig（session-manager.json）を正とし、フロントマターは「表示用 + 公式ツール連携用」の派生データとする。CSMによる書き込み時のみ同期。ユーザーがフロントマターを直接編集した場合はCSMが検出して同期確認ダイアログを表示。

5. effortパラメータへの移行

公式推奨の変更

項目旧新（公式推奨）
深度制御 budget_tokens / maxThinkingTokens effort（low/medium/high/max）
Extended Thinking thinking: {type: "enabled", budget_tokens: N} thinking: {type: "adaptive"} + effort
CLIフラグ MAX_THINKING_TOKENS 環境変数 --effort フラグ

CSMの現状

  • AgentConfig に effort (4段階) + thinkingEnabled + maxThinkingTokens の3フィールドが存在
  • cliBuilder.ts は --effort と MAX_THINKING_TOKENS 環境変数の両方を出力
  • フォームUI は effort 4段階 + thinking トグル + maxThinkingTokens 数値入力

判断: 採用 — Phase 1

変更内容:
  1. maxThinkingTokens フォームフィールドに「非推奨」ラベルを追加。effortの説明文に「effort パラメータが公式推奨です」と明記
  2. thinkingEnabled トグルを effort と連動させる: effort が設定されている場合、thinking は自動で adaptive に
  3. cliBuilder.ts: effort が設定されていれば MAX_THINKING_TOKENS 環境変数は出力しない（effortが優先）
  4. 将来（Phase 3）で thinkingEnabled と maxThinkingTokens を AgentConfig から削除予定
リスク: 既存ユーザーが maxThinkingTokens を精密に設定している場合に effort 移行で意図が変わる。
対策: 非推奨化のみで削除はしない（Phase 1）。effort 未設定時は従来通り maxThinkingTokens を使用。マイグレーションガイドを CHANGELOG に記載。

6. スキルの段階的開示（L1→L2→L3）

公式パターン

  • L1: スキル名と説明のみ（常時ロード、最小コンテキスト消費）
  • L2: 完全なSKILL.md本文（関連性判断時にロード）
  • L3: リンクファイル群（必要時のみ個別ロード）

→ スキルは実質的に無制限のコンテキストをバンドル可能

CSMメモリ管理への適用可能性

  • CSMのメモリ管理は ~/.claude/projects/*/memory/ のフラットファイル構造
  • MEMORY.md がインデックス（ポインタ）、各メモリファイルが詳細
  • 既に L1（MEMORY.md）→ L2（個別ファイル）の2段階構造を実現

判断: 見送り

理由:
  • CSMのメモリ管理は既に「MEMORY.md インデックス + 個別ファイル」で段階的開示を実現している
  • L3（リンクファイル群）のパターンはスキルのような大規模参照資料向けであり、メモリ管理の用途（ユーザー情報・フィードバック・プロジェクト知識）には過剰
  • メモリファイルは典型的に 200行未満であり、段階的開示の恩恵が小さい
  • 将来的にCSM管理のスキル機能を実装する際には改めて検討

9. リスクと対策

#リスク影響度発生確率対策
R1 Agent SDK TypeScript版のAPI変更・非互換 高 中 抽象レイヤーで切替可能に。JSONL直接をデフォルト維持
R2 フック増加によるセッション遅延 中 低 全CSMフック async:true + timeout:10。累積影響を計測
R3 .agent-rules と .claude/agents の二重管理混乱 高 中 CSM管理 (.agent-rules) を正とする明確な優先度ルール。名前衝突警告UI
R4 YAMLフロントマターとAgentConfigの不整合 中 中 AgentConfigを正（Single Source of Truth）。フロントマターは派生データ
R5 maxThinkingTokens非推奨化でユーザー混乱 低 低 非推奨ラベル表示のみ。削除はPhase 3。CHANGELOGに移行ガイド
R6 公式フック仕様の変更（24種→追加/削除） 中 低 各フックスクリプトは独立。不要になったら settings.json から除外するだけ
