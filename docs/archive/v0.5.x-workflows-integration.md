## 0. エグゼクティブサマリ

- Claude Code **2.1.154** で動的ワークフローが正式化：「ワークフローを作って」と頼むと tens〜hundreds のエージェントが **バックグラウンドオーケストレーション** され、`/workflows` で確認可能
- `/workflows` は **インタラクティブセッション内のスラッシュコマンド**であり、CLI からは独立サブコマンドとして存在しない（実機 `claude workflows --help` は `claude --help` にフォールバックする — 確認済 2026-05-28）
- 取得経路は **`claude agents --json`** が事実上のマスタ。workflow 由来のエージェントも同 JSON に列挙される（`kind` フィールドで判別可能と推定）
- 採用方針：**3 段階導入**（Phase A 表示 → Phase B 制御 → Phase C 組織図統合）

## 1. 設計目標

### 1.1 ユーザーストーリー

> **US-1**：CSM ユーザーとして、`/workflows` で起動した数十のエージェントを CSM サイドバーで一覧できる。
>
> **US-2**：workflow 由来の子エージェント群を **1ノード** として組織図に表示し、展開で個別エージェントが見える。
>
> **US-3**：暴走しているワークフローを CSM から停止できる（将来）。
>
> **US-4**：workflow に対応していない環境でも CSM は壊れず、既存の `claude agents` 統合だけ動く。

### 1.2 達成基準（KPI）

| 指標 | 目標値 |
|---|---|
| workflow 由来エージェントの認識率 | 95%以上（`kind` フィールド or 親子推定で判別） |
| 100 個の workflow エージェント表示遅延 | < 1.5秒 |
| 組織図描画（workflow 含む 200 ノード） | 60fps 維持 |
| `/workflows` 機能不在時のフォールバック | 既存 `claude agents` 表示を維持・エラーなし |

### 1.3 スコープ外（v0.5.x で扱わない）

- CSM からの **ワークフロー起動**（VS Code から「ワークフローを作って」と発火）
- ワークフローテンプレート編集
- 他PC（リモート）のワークフロー結果取得
- ワークフロー履歴の永続保存

## 2. 実機調査結果（2026-05-28 Claude Code 2.1.158）

### 2.1 確認できた仕様

| 項目 | 結果 |
|---|---|
| `claude workflows` 独立サブコマンド | **存在しない**（`claude --help` にフォールバック） |
| `/workflows` スラッシュコマンド | **インタラクティブセッション内のみ** |
| `claude agents --json` | ✅ JSON出力対応（pid/cwd/kind/startedAt/sessionId） |
| `claude agents --cwd <path>` | ✅ ワークスペース絞り込み可 |
| `claude --bg --exec <cmd>` | ✅ バックグラウンド実行（task tool 経由） |
| `claude plugin list` | ✅ プラグイン一覧取得可 |

### 2.2 claude agents --json サンプル出力（実測）

```json
[
  {
    "pid": 561740,
    "cwd": "/mnt/hgfs/Project/claude-session-manager",
    "kind": "interactive",
    "startedAt": 1780147309214,
    "sessionId": "ff17eb16-21d9-450f-88db-5a501a8e2ef4"
  },
  ...
]
```

**重要**：現状の `kind` は `interactive` のみ観測。**workflow / background 由来のセッションがどの `kind` 値で返されるかは未確認** → Phase A の T6.1 で実機確認必須。

### 2.3 ワークフロー検出の推定戦略

`kind` フィールドが workflow を識別できなかった場合のフォールバック：

1. **親子関係推定**：1つの sessionId 配下に複数の sidechain (`agent-a*`) が短時間で生成される → workflow と推定
2. **時系列クラスタリング**：同一 cwd で 5秒以内に 10+ セッションが立ち上がる → workflow 起動と推定
3. **JSONL コメント**：`~/.claude/projects/<key>/*.jsonl` に workflow メタが含まれる可能性 → 要調査

## 3. アーキテクチャ

### 3.1 サービス階層

```
[Polling Timer (5s, visibility-aware)]
        │
        ▼
[ClaudeAgentsService.fetchJson()]   ◀── 既存
        │
        ▼
[WorkflowClassifier (新規)]
   ├─ entries[].kind === 'workflow' → workflow
   ├─ 親子推定（sessionId 配下の sidechain 数）
   └─ 時系列クラスタリング
        │
        ▼
[WorkflowGroupedView]
   ├─ workflow_id (推定 or 抽出)
   ├─ workflow_name (cwd + 起動時刻から命名)
   ├─ children: ClaudeAgentEntry[]
   └─ status: running / completed
        │
        ▼
[agentLiveTreeProvider] 「🌀 ワークフロー」セクション
        │
        ▼ (click)
[既存 previewSession / openInClaude]
```

### 3.2 新規ファイル設計

```
src/services/
  workflowClassifier.ts    # 新規：claude agents 出力を workflow グループに分類
  workflowService.ts        # 新規：WorkflowGroupedView の組み立て・キャッシュ

src/providers/
  agentLiveTreeProvider.ts  # 既存に「🌀 ワークフロー」セクション追加

src/panels/
  orgChartPanel.ts          # 既存にワークフロー実行グラフ重畳機能
```

### 3.3 データモデル

```typescript
// src/services/workflowClassifier.ts
export interface WorkflowGroup {
  id: string;                     // 推定 ID（sessionId or cwd+startedAt のハッシュ）
  displayName: string;             // "ワークフロー: <cwd basename> (12:34)"
  rootSessionId?: string;          // ワークフローを起動した親セッション
  cwd: string;
  startedAt: number;
  status: 'running' | 'completed' | 'mixed';
  children: ClaudeAgentEntry[];    // 既存型
  childCount: number;              // children.length のキャッシュ
  classificationReason: 'kind-field' | 'sidechain-cluster' | 'time-cluster';
}

export interface WorkflowClassificationResult {
  workflows: WorkflowGroup[];
  ungroupedAgents: ClaudeAgentEntry[];  // workflow に属さない単独エージェント
}
```

### 11.2 データソース

#### 11.2.1 取得経路（実機調査 2026-05-30 確認）

| 経路 | 実現性 | 内容 |
|---|---|---|
| `claude /workflows`（インタラクティブ内） | ❌ CLI からは叩けない | スラッシュコマンドのみ |
| `claude workflows --help` | ❌ サブコマンド非存在 | CLI 経路なし |
| **`claude agents --json`** | ✅ **正式 API** | **これが唯一のマスタソース** |

**重要発見**：`claude agents --help` のオプション説明に **"dispatched sessions"** 文言が随所に出現する：
- `--agent <agent>`: "Default agent for sessions dispatched from agent view"
- `--effort <level>`: "Default effort level for sessions dispatched from agent view"

→ `claude agents` view 経由で起動 (dispatch) された子セッション、つまり **workflow から派生したエージェント群も `--json` の戻り値に含まれる**ことが裏付けられた。これにより：

> **結論**：オーケストレーション可視化タブの **データソースは `claude agents --json` 一本でよい**。`/workflows` への直接アクセスは不要。

#### 11.2.2 取得データ → 表示モデル変換

```
[claude agents --json] (5秒ポーリング)
        │
        │  raw: [{pid, cwd, kind, startedAt, sessionId}]
        ▼
[ClaudeAgentsService.fetchJson()]  ◀── 既存
        │
        ▼
[WorkflowClassifier]  ◀── 既存（§3.2 で定義済）
   ├ workflows: WorkflowGroup[]
   └ ungroupedAgents: ClaudeAgentEntry[]
        │
        ▼
[OrchestrationViewModel] ← 新規追加
   ├ workflows: WorkflowGroup[]
   │    ├ progress: {running, done, blocked, total}
   │    ├ timeline: TimelineSegment[]  ◀── 開始〜完了
   │    └ dispatchTree: DispatchNode    ◀── 親子推定木
   ├ singleAgents: ClaudeAgentEntry[]
   └ overlay: { activeSessionIds: Set<string> }  ◀── 組織図用
```

#### 11.2.3 親子（dispatch）関係の推定

`claude agents --json` には親子関係フィールドが**ない**ため、以下の信号を組み合わせて推定：

| 信号 | 用途 |
|---|---|
| `sessionId` | ノード ID |
| `cwd` 一致 | 同じワークスペース由来の可能性大 |
| `startedAt` の時系列 | 親 → 子の順序付け |
| `~/.claude/projects/<key>/*.jsonl` の `parentUuid` | **既存 sessionLoader 経由で取得可能** — 親子関係のグランドトゥルース |
| `kind` フィールド | "interactive" 以外（"dispatched" 等が確認できれば） |

**実装方針**：jsonl からの `parentUuid` 抽出を **dispatchTree 構築の主役** とし、`claude agents --json` は live status を提供する補助役とする。**既存 `sessionLoader.ts` が再利用できる**。

#### 11.2.4 ポーリング戦略

| データ | 取得経路 | 間隔 |
|---|---|---|
| ライブ状態 | `claude agents --json` | 5秒（既存・タブ可視時のみ） |
| dispatchTree | jsonl 読み直し（増分） | 5秒（live と同期） |
| タイムライン | dispatchTree から計算 | 同上 |
| overlay activeSessionIds | live から導出 | 同上 |

**キャッシュ**:
- WorkflowGroup / DispatchNode はメモリのみ（TTL 5分）
- jsonl は **mtime ベースの増分読み込み**（既存 sessionLoader の機構を活用）

```
│ [サマリーバー]                               │
│  📊 5 workflows • 47 agents (🟢32 / ⏳3 / ✅12)│
│                                              │
│ [ツリービュー（左1/2）] [タイムライン（右1/2）]│
│  workflow-A                  ├─■─■─■─       │
│   ├─ planner                 │ ├─■─        │
│   │   ├─ impl-1              │ │ ├─■─■─    │
│   │   ├─ impl-2              │ │ ├─■─      │
│   │   └─ impl-3              │ │ └─■─■─    │
│   └─ qa                      │ └─■─■─■─    │
│  workflow-B                  ├─■─■─■─■─   │
│                                              │
│ [タブ下部] 単発ライブセッション一覧          │
└─────────────────────────────────────────────┘
```

| 項目 | 評価 |
|---|---|
| メリット | 視認性◎ / 既存 Cytoscape 知見 流用 / リッチな可視化 |
| デメリット | 実装コスト大 / Webview 維持コスト |
| 実装コスト | 中〜大（5〜7日） |

#### 案B: TreeView でネスト表示（VS Code 標準）

```
🎼 オーケストレーション
├ 📊 サマリー (5 workflows / 47 agents)
├ 🌀 workflow-A [12 agents, running]
│   ├ 🟢 planner [00:12:34]
│   │   ├ 🟢 impl-1 [00:05:21]
│   │   ├ ⏳ impl-2 [waiting]
│   │   └ ✅ impl-3 [done in 03:42]
│   └ 🟢 qa [00:08:00]
├ 🌀 workflow-B [8 agents, done]
└ ▼ 単発セッション (3)
    ├ 🟢 director [01:30:12]
    └ ...
```

| 項目 | 評価 |
|---|---|
| メリット | 実装軽量 / VS Code TreeView 標準で挙動安定 / 既存 agentTreeProvider 知見 流用 |
| デメリット | タイムライン表示が難しい（columns 表現に弱い） |
| 実装コスト | 小〜中（2〜3日） |

#### 案C: 既存組織図にライブオーバーレイ（色付けのみ）

既存 `orgChartPanel.ts` のノードに、**動作中エージェントだけ緑バッジ／脈動アニメ**を載せる。新タブを作らず、組織図タブの一機能として実現。

| 項目 | 評価 |
|---|---|
| メリット | 新タブ不要 / 既存組織図と完全統合 / 実装最軽量 |
| デメリット | "5つ目のタブ" というユーザー発案を満たさない / タイムラインなし |
| 実装コスト | 小（1〜2日） |

#### 採用方針（推奨）

> **B → A のハイブリッド進化**：
> - **Phase 1**：案B（TreeView）で素早く提供（実装軽量・既存知見活用）
> - **Phase 2**：案A 相当の Webview ガント・ツリーを別ペインとして追加（折りたたみ可能）
> - **Phase 3**：案C を **組織図タブ側に追加** して相互参照（オーケストレーションタブから「組織図で見る」ボタン、組織図から「オーケストレーションで見る」ボタン）

→ Cの「組織図オーバーレイ」は新タブの代替ではなく、**両タブを行き来する補完機能**として位置づける。

### 11.7 リスク

| # | リスク | 緩和策 |
|---|---|---|
| OR1 | 親子推定が jsonl 依存で、jsonl 未生成時の workflow に弱い | claude agents の time-cluster 戦略でフォールバック（既存 §3.3） |
| OR2 | タイムライン描画コストが 2000 ノードで重い | virtualization + viewport limit（30分過去まで） |
| OR3 | 5タブ化で UI が肥大化、エージェント/プロジェクトと役割重複 | 設定 `orchestration.enabled` で OFF 可、初期はデフォルト ON だが「使わない人は閉じられる」 |
| OR4 | Webview のライフサイクル管理がタブ切替で複雑化 | mainTabPanel のタブ可視管理を Phase 1 段階で堅牢化 |
| OR5 | workflow 概念がユーザーに伝わらない | サマリーバーに「ワークフロー＝Claude が自動編成した複数エージェント」ツールチップ |
