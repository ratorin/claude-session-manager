### 0.2 最重要発見 4 件

1. **【公式重複の解消は済・ただし死蔵】** `claude agents --json`（TTY必須）連携は **既定 `enabled:false` で「廃止予定」と明記済**（package.json L1014-1018）。にもかかわらず `claudeAgentsService` は `extension.ts` で生成・配線されたまま（L251-270）。**実機の `~/.claude/sessions/*.json` は `claude agents --json` と同一フィールド（pid, cwd, kind, startedAt, sessionId, version, entrypoint）を TTY 不要で保持している**。→ **公式 API に寄せるのではなく、CSM のファイル監視に一本化するのが正解**（後述 R-1）。

2. **【陳腐化の誤検知に注意】** 既存 `feature-audit.md` の「P0：`cliBuilder.MODEL_MAP['opus']='claude-opus-4-6'` で固定」は **既に解消済**。現行 `cliBuilder.ts` は `modelCliMap` でエイリアス（`'opus'→'opus'`）を書き出し、CC 側で最新モデルへ解決させる方式（L16-21）。**feature-audit.md のこの記述は stale**。

3. **【ライブ・サブエージェント検出が新構造を未活用】** CC は各サブエージェントを `projects/<proj>/<sid>/subagents/agent-*.jsonl` ＋ `agent-*.meta.json`（`{agentType, description}`）に出力する。`sessionLoader.readSubagentMeta`（履歴ビュー）は対応済だが、**ライブ検出 `subagentDetector.ts` は親JSONL末尾の `tool_use`/`tool_result` ヒューリスティックのみ**で、権威ある meta.json を読まない。

4. **【`/csm-ask-agent` の "nohup" 懸念は該当なし】** タスク観点で挙がっていた「nohup & 方式で完了通知が来ない問題」は **存在しない**。`templates/csm-ask-agent.command.md` は `run_in_background: true`（CC の Bash バックグラウンド機能）を使用しており（L79）、完了検知は機能する。**現状維持で良い**。

## 3. 代替案（具体策・優先度付き）

### R-1【最優先】`claude agents` 連携を撤去し、`sessions/*.json` 由来のリッチ・ライブ監視に一本化
- **根拠**：実機 `sessions/466995.json` は `claude agents --json` と同フィールドを **TTY 不要・追加プロセス不要**で保持。型 `SessionMeta`（types.ts L27-34）に `kind`/`entrypoint` も既に存在。
- **やること**：
  1. `agentWatcher.update()`（L285-289）で `data.kind`/`data.entrypoint`/`data.startedAt`/`data.version` も読み取り、states に保持。
  2. `orchestrationViewModel` の `kind` 供給元を agentWatcher に変更 → B-2 解消（interactive/background が実データで動く）。
  3. `claudeAgentsService.ts`（約516行）と `extension.ts:251-270` の配線を撤去（または上記読込へ転用）。
  4. package.json の `claudeAgentsIntegration.*`（4キー）を deprecate/削除。
- **効果**：公式重複の解消＋ workflow/kind 判別の取りこぼし回収＋デッドコード除去を **一手で達成**。TTY 制約問題は構造的に消滅。

### R-2 ライブ・サブエージェント検出を `subagents/*.meta.json` 優先に改修
- `subagentDetector`（または呼び出し側 agentWatcher L355 / orchestrationViewModel L131）で、対象セッションの `subagents/agent-*.meta.json` を読み `agentType`/`description` を権威ソースとして採用。末尾 `tool_use` ヒューリスティックは in-flight 検出用フォールバックに。
- **効果**：D-2 解消。ライブ表示・オーケストレーションでサブエージェント種別が正確に出る。

### R-3 陳腐化トークンの掃除（低リスク・即時）
- S-1（effort `max` の有効性確認 → 不要なら除去・コメント更新）、S-2（haiku モデルIDのエイリアス化/集約）、S-3（未宣言 `detectionMode` リスナー撤去）、S-4（投機的テキストパーサ撤去＝R-1 同伴）、S-6（生成メモリ文言）。

### R-4 タスク状態を公式 hook 駆動へ
- `TaskCompleted` / `Stop`(background_tasks) hook を `hookService` で配備し、`taskTracker` の状態遷移を hook イベントで確定。mtime 閾値はフォールバックに降格 → 対話無操作の `error` 誤検知（taskTracker L48-52）を解消。

### R-5 資料整合（feature-audit.md 追補）
- S-5 の通り、feature-audit.md の「P0 MODEL_MAP」「claude agents ◎対応済」を現状（解消済/死蔵）に更新。設計判断の基礎資料を正す。

## 4. csm-planner への申し送り（今後設計の論点）

1. **「公式に寄せる」≠「公式コマンドを叩く」**：本件最大の学び。`claude agents --json` は TTY 必須で IDE 拡張から使えないが、**その出力源 `sessions/*.json` は公式が吐くファイルでありファイル監視で同等データが得られる**。CSM の独自実装（agentWatcher）の方が CC のファイル契約に直結しており堅い。→ 設計方針は「公式 CLI への依存を増やす」より「公式が吐くファイル契約に追従する」を推奨。

2. **死蔵コードの会計**：`claudeAgentsService` は「対応済 ◎」と評価されていたが実体は既定無効の死蔵。**“実装済” と “既定で動作” は別**。今後の audit は「default config で到達するか」を判定軸に含めるべき。

3. **オーケストレーション/ワークフロー可視化の前提**：`/workflows`・background agents の可視化を設計するなら、データ源は `sessions/*.json`（kind/entrypoint）＋ `subagents/*.meta.json` の二本立てが現実的。`isWorkflowLike` の `subagents>=3` ヒューリスティック（orchestrationViewModel L143）は暫定であり、`kind`/`entrypoint` 実データへの置換が前提。

4. **モデル/effort はエイリアス方針が正解**：`modelCliMap` のエイリアス化は秀逸でリリース追従コストを消した。effort も `max` のような世代依存値を持たず、CC 解決に委ねる方針を維持・徹底（S-1）。

5. **テスト不足**：CC 仕様（sessions/*.json スキーマ、subagents meta、CLI 引数）に密結合する割に回帰テストが1本。CC バージョン更新時の破壊を検知する最小スイートを設計段階で要件化。

6. **`/csm-ask-agent` は健全**：`run_in_background` 採用済で完了通知問題はない。ここに工数を割く必要はない（誤った課題設定を排除）。
