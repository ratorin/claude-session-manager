CSM エージェント別 TODO.md 自動管理 設計仕様書

バージョン: Draft 1.1 | 作成日: 2026-04-05 | 品質管理部レビュー反映済 | 対象: CSM v0.4.0 | 作成: CSM開発部

1. 背景と目的

問題

TodoWrite ツールで管理するタスクはセッション終了時に消失する。次のセッションでは未完了タスクの存在すら知らない。

3層ToDo管理パターン

層手段寿命粒度現状
長期GitHub Issues / Asana永続エピック・ストーリー外部管理
中期TODO.md（本設計）セッション横断タスク・サブタスク欠落
短期TodoWriteセッション内実装ステップ既存

目的

CSMにエージェント別TODO.md自動管理を組み込み、中期層を埋める。セッション終了時にTodoWriteの未完了タスクを永続化し、次のセッションで自動復元する。

5. Stopフックによる自動フラッシュ

5.1 フック発火タイミング

Claude Code の Stop フックはセッション応答完了時に発火する。 CSMはこのタイミングで以下の処理を実行する。

処理フロー

  1. Stop フックが発火
  2. セッションID取得（優先順位）: HIGH-1 対応
    1. 主系: JSONL ファイル末尾から sessionId フィールドを抽出（最も確実）
    2. 副系: 環境変数 $SESSION_ID（Claude Code が提供する場合）
    3. 失敗時: TODO.md を更新せず、stderr にエラーログのみ出力して終了（exit 0）
  3. session-manager.json を読み、該当セッションIDに紐づくエージェントを特定
  4. セッションの JSONL ファイル末尾から TodoWrite の最終状態 を抽出
  5. 該当エージェントの TODO.md を更新:
    • TodoWrite の未完了タスク → ## 未完了 セクションにマージ
    • TodoWrite の完了タスク → ## 完了 セクションに追記
    • 重複検出（優先順位）: HIGH-2 対応
      1. 主キー: TodoWrite の id フィールドと TODO.md の <!-- id:xxx --> コメントで照合
      2. フォールバック: id が無い手動追記タスクのみ、タスク内容の先頭40文字でマッチング

5.3 パスサニタイズ（セキュリティ） CRITICAL-1 対応

必須: todo-flush.js は VSCode 拡張の外側で動作するため、CSM 本体の validateOutputFile() や sanitizeForAutoSection() のガードが効かない。以下のサニタイズを必ず実装すること:
  1. AgentConfig.name から ..、絶対パス成分（/ 先頭、C:\ 等）、制御文字を除去
  2. path.resolve() 後に、結果パスが許可ベースディレクトリ（ruleFolder）配下であることを検証
  3. 検証失敗時はエラーログを出力して当該エージェントをスキップ（他エージェントの処理は継続）
// パスサニタイズ例
function sanitizeAgentName(name: string): string {
    return name.replace(/[\/\\\.]{2,}/g, '').replace(/^[\/\\]/, '');
}
function validatePath(resolved: string, baseDir: string): boolean {
    const normalBase = path.resolve(baseDir);
    const normalTarget = path.resolve(resolved);
    return normalTarget.startsWith(normalBase + path.sep);
}

5.7 ロックファイル設計 MEDIUM-1 対応

同時書き込み防止のため .TODO.md.lock を使用する。スタレロック対策を含む:

// ロックファイル内容: { "pid": 12345, "createdAt": "2026-04-05T09:25:00Z" }
// 取得手順:
// 1. .TODO.md.lock の存在チェック
// 2. 存在する場合:
//    a. ロックファイル内の pid が生存しているか確認（process.kill(pid, 0)）
//    b. pid が死んでいる → スタレロック。強制解除して再取得
//    c. pid が生存 + 作成から5秒以内 → 待機（100msポーリング、最大5秒）
//    d. pid が生存 + 作成から5秒超過 → スタレロック。強制解除
// 3. ロック取得: 自身の pid + 現在時刻を書き込み
// 4. 処理完了後: ロックファイルを削除（finally ブロック）

7.3 FileSystemWatcher による自動更新 MEDIUM-4 対応

// extension.ts — TODO.md 変更監視（プロジェクト + グローバル両方）
function watchTodoFiles(context: vscode.ExtensionContext, ruleFolder: string, globalRuleFolder: string) {
    // プロジェクトスコープ
    const projectWatcher = vscode.workspace.createFileSystemWatcher(
        new vscode.RelativePattern(ruleFolder, '*/TODO.md')
    );
    // グローバルスコープ（取締役等）
    const globalWatcher = vscode.workspace.createFileSystemWatcher(
        new vscode.RelativePattern(globalRuleFolder, '*/TODO.md')
    );
    const refresh = () => agentProvider.refresh();
    for (const w of [projectWatcher, globalWatcher]) {
        w.onDidChange(refresh);
        w.onDidCreate(refresh);
        w.onDidDelete(refresh);
        context.subscriptions.push(w);
    }
}

8.3 AgentWatcher への追加 MEDIUM-6 対応

// agentWatcher.ts — onSubagentComplete イベント追加

// 新規イベント
private readonly _onSubagentComplete = new vscode.EventEmitter<SubagentCompleteEvent>();
readonly onSubagentComplete = this._onSubagentComplete.event;

// hasChanged() 拡張: 前回の activeSubagentIds との差分で完了を検知
private previousSubagentIds = new Set<string>();

private detectCompletedSubagents(current: SubagentInfo[]): void {
    const currentIds = new Set(current.map(s => s.toolUseId));
    for (const prevId of this.previousSubagentIds) {
        if (!currentIds.has(prevId)) {
            // prevId が消えた = 完了
            this._onSubagentComplete.fire({
                parentSessionId: this.sessionId,
                childSessionId: '', // tool_result から取得
                childAgentName: this.previousSubagentMap.get(prevId)?.name ?? '',
                todoRemaining: 0,   // TODO.md パース後に設定
                completedTodos: [],
                result: '',
            });
        }
    }
    this.previousSubagentIds = currentIds;
}

9.2 移行のアトミック性とロールバック HIGH-3 対応

設計方針: 移行は完全にアトミックにはできないが、各ステップを冪等に設計する。
  • 各ステップは「既に完了済みならスキップ」で実装。中断後に再実行すれば途中から継続
  • ステップ実行前に .agent-rules/.migration-state.json に進行状況を記録
  • ロールバックコマンド claudeManager.rollbackMigration を提供:
    • .trash/ からフラット構造の旧ファイルを復元
    • session-manager.json の ruleFile パスを旧パスに復元
    • 新規作成したフォルダ構造は .trash/ に移動
  • 移行完了後、.migration-state.json に "status": "completed" を記録

9.4 後方互換性

重要: 移行は段階的に行う。
  • CSMはフラット構造（.agent-rules/X.md）とフォルダ構造（.agent-rules/X/X.md）の両方を認識する
  • ruleFile パスが直接ファイルを指していればそのまま使用（フラット構造）
  • ruleFile パスがディレクトリを指していれば <dir>/<dirname>.md をルールファイルとして解決（fs.stat で判定）
  • 移行コマンド claudeManager.migrateToFolderStructure を提供（手動実行）

13. リスクと対策

リスク影響対策
Stop フックが発火しない場合がある（強制終了等） TodoWrite の内容がフラッシュされない セッション開始時に前回の JSONL を遡って TodoWrite を復元する「リカバリモード」を用意
TODO.md の同時書き込み競合 ファイル破損 ロックファイル使用（PID + 作成時刻記録、スタレロック自動解除）
移行時に既存のルールファイルが壊れる エージェントが起動不能 冪等な移行ステップ + .migration-state.json で進行管理 + ロールバックコマンド
TodoWrite のフォーマットが変わる可能性 パーサーが動作しない パーサーを緩く設計（未知フィールドは無視）。バージョン検出を入れる
TODO.md の肥大化 ルール読み込みコスト増大 完了タスクは直近10件のみ保持。超過分は HISTORY.md に転記
パストラバーサル攻撃 任意ファイルの上書き エージェント名サニタイズ + path.resolve() 後のベースディレクトリ検証（CRITICAL-1）
HISTORY.md の無限成長 ディスク圧迫・コンテキスト圧迫 20世代 or 50KB の上限。超過分は古いエントリから削除
