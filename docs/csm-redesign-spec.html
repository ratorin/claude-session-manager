1. 現状の問題点と廃止する機能

問題 1: 子エージェント検知不能

根本原因を解決
現状~/.claude/sessions/*.json のPID生存チェックのみ。--resume --print パイプ起動の子エージェントは sessions/ にJSONを作らないため検知できない
根本原因sessions/*.json は対話的CLIのみが生成する。子エージェントの起動は親のJSONLに tool_use(Task/Agent) として記録される
解決方針親セッションのJSONL解析で子エージェント起動を検出する方式に変更。sessions/*.json のPID方式は補助として併用

問題 2: 取締役（自分自身）が表示される

フィルタ追加
現状updateStatusBar() が dataStore.getAgents() の全エージェントを走査。取締役も子エージェントも区別なくカウント
根本原因フィルタリングが未実装
解決方針parentAgent フィールドで判定。parentAgent を持つエージェント（＝子エージェント）のみを監視対象にする。取締役名のハードコード（if (a.name === '取締役')）も廃止

問題 3: 点滅しない

代替表現に変更
現状VS Code TreeItem / StatusBarItem にアニメーション機能がない。静的アイコン切り替えのみ
解決方針点滅は諦め、以下の代替表現で「稼働感」を伝える:
(1) アイコン色変化: 🟢実行中 / ⬜停止 / 🟡応答待ち
(2) ツールチップにタスク名・経過時間を表示
(3) ステータスバーにスピナー文字を利用した擬似アニメーション（⠀⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏ のローテーション）

問題 4: agentMonitor.ts がデッドコード（109行）

廃止 → 新モジュールに置換
現状agentMonitor.ts は import もされていない完全なデッドコード。extension.ts L18 にコメント「将来利用」が残存
解決方針旧 agentMonitor.ts を削除し、新モジュール agentWatcher.ts に置換。
旧モジュールの JSONL 解析ロジック（末尾読み取り + tool_use/tool_result ペア追跡）は新モジュールに発展的に引き継ぐ

問題 5: enableAgentMonitor OFF でも監視が動作する

完全停止を保証
現状sessionTreeProvider.startWatching() は enableAgentMonitor と無関係に常時稼働。OFFでもセッション一覧の緑丸が出る
根本原因ライブセッション検出（fs.watch + ポーリング）と「エージェント監視」設定が分離されていない
解決方針enableAgentMonitor = false 時は一切のJSONL解析・PIDチェック・ポーリングを停止。
セッション一覧のライブ表示も無効化する（アイコンは通常表示に統一）

問題 6: 取締役名がハードコード

parentAgent判定に統一
現状agentTreeProvider.ts L73-74: if (a.name === '取締役') return -1
解決方針ハードコード廃止。ソート最上位の判定を !agent.parentAgent（トップレベル）で行う。
取締役は「parentAgentが未設定のエージェント」として自動判定される

問題 7: タイマーが2つ並走

1つに統合
現状extension.ts の agentPollTimer と sessionTreeProvider.ts の pollTimer が同じ間隔で並走
解決方針新モジュール agentWatcher.ts に統合。1つのタイマーで JSONL解析 + PIDチェック + UI更新をすべて処理

廃止するファイル・関数一覧

src/agentMonitor.ts — 旧JNOLモジュール（109行、完全未使用）→ 削除
sessionTreeProvider.ts: startWatching() — fs.watch + pollTimer → agentWatcher.ts に移管
sessionTreeProvider.ts: restartPolling() — 同上
sessionTreeProvider.ts: stopWatching() — 同上
sessionTreeProvider.ts: updateLiveSessions() — 同上
sessionTreeProvider.ts: isProcessAlive() — agentWatcher.ts に移管
extension.ts: agentPollTimer — agentWatcher.ts に統合
extension.ts: updateStatusBar()内のfor-of — agentWatcher のイベントに置換
agentTreeProvider.ts L73-74 — if (a.name === '取締役') ハードコード廃止

3. 各コンポーネントの責務

agentWatcher.ts

新規作成 Phase 1c
責務エージェント監視の唯一のエンジン。PID検出 + JSONL解析 + 状態管理 + イベント発火
入力 (1) ~/.claude/sessions/*.json — PID生存チェック用
(2) 取締役セッションJSONL — tool_use(Task/Agent) 検出用
(3) subagents/ フォルダ — 子エージェントJSONL（存在する場合）
出力 AgentWatcherState オブジェクト + 'change' イベント
タイマー単一の setInterval。enableAgentMonitor 設定で ON/OFF。agentMonitorInterval で間隔制御
キャッシュmtime + size キャッシュ（旧 agentMonitor.ts から引き継ぎ）。変更なければ再解析しない

公開API

  • start(): void — 監視開始。enableAgentMonitor=false なら何もしない
  • stop(): void — 監視停止。タイマー・watcher をすべてクリア
  • restart(): void — 設定変更時に呼ぶ。stop() → start()
  • getState(): AgentWatcherState — 現在の監視状態を取得
  • isLive(sessionId: string): boolean — セッションがライブか
  • on('change', callback): void — 状態変化イベント
  • dispose(): void — リソース解放

AgentWatcherState 型定義

  • liveSessionIds: Set<string> — PID生存中のセッションID
  • activeSubagents: Map<string, SubagentInfo> — 稼働中の子エージェント（agentName → タスク情報）
  • directorActive: boolean — 取締役セッションが稼働中か

SubagentInfo 型定義

  • toolUseId: string — tool_use の ID
  • taskDescription?: string — Agent ツールの description 引数（ツールチップ表示用）
  • startedAt: Date — 検出時刻（経過時間表示用）

新規作成 Phase 1c

入力AgentConfig オブジェクト

4. タイマー統合設計

統合タイマーの仕様

タイマー数1つのみ（agentWatcher.ts 内の setInterval）
間隔claudeManager.agentMonitorInterval 秒（デフォルト: 5秒）
ON/OFFclaudeManager.enableAgentMonitor で制御。false 時はタイマーを開始しない
リアルタイム監視fs.watch(~/.claude/sessions/) — PIDファイルの追加・削除を即座に検出。ポーリングの補完
agentWatcher.start()
  ├─ enableAgentMonitor === false → 何もしない。return
  ├─ fs.watch(~/.claude/sessions/) → PIDファイル変更時: tick()
  └─ setInterval(tick, interval * 1000) → 定期実行

tick()
  ├─ (1) updateLiveSessions() → sessions/*.json のPIDチェック
  ├─ (2) analyzeDirectorJSONL() → 取締役JNOLの tool_use/tool_result 解析
  ├─ (3) 状態が前回と異なるか比較
  └─ (4) 変化あり → emit('change') → StatusBar + AgentTree + SessionTree 更新
enableAgentMonitor OFF 時の保証:
agentWatcher.start() が何もしない → タイマーなし、fs.watch なし、JSONL読み取りなし。
agentWatcher.isLive() は常に false を返す。
セッション一覧のライブアイコン（緑丸）も表示されない。
ステータスバーは 👥 N（静的表示、tooltip: 「エージェント監視: OFF」）。

5. 表示設計（点滅代替・フィルタ）

ステータスバー

監視 OFF👥 N（エージェント総数）/ tooltip: 「エージェント監視: OFF」/ 通常色
稼働ゼロ👥 N / tooltip: 「動作中のエージェントなし」/ 通常色
稼働あり⠋ N/M ← スピナー文字 + 稼働数/総数
tooltip: 「動作中: N件\n▶ CSM開発部 (🔍探索 2:30経過)\n▶ テスト部 (📋計画 0:45経過)」
backgroundColor: warningBackground

スピナー擬似アニメーション

  • ブライユ点字パターン文字を使用: ⠋ ⠙ ⠹ ⠸ ⠼ ⠴ ⠦ ⠧ ⠇ ⠏
  • 200ms間隔で文字を切り替え（ポーリングタイマーとは別のアニメーション用タイマー）
  • 稼働中エージェントが 0 になったらアニメーション停止
  • VS Code StatusBarItem.text の更新のみで実現（API制約なし）
表示対象の変更:
旧: 全エージェント（取締役含む）をカウント
新: parentAgent を持つエージェント（子エージェント）のみをカウント。
取締役は「管理者」であり監視対象ではない。

エージェント管理サイドバー（AgentTree）

running🟢 circle-filled + terminal.ansiGreen（変更なし）
pending🟡 circle-filled + terminal.ansiYellow（JSONL解析で tool_use 送信済み but 応答なし = 応答待ち）
idle⬜ circle-outline + foreground（変更なし）
unlinked⬜ circle-outline + disabledForeground（変更なし）

ソート順の変更

  • if (a.name === '取締役') return -1 → !a.parentAgent でトップレベル判定
  • トップレベル（parentAgent 未設定） → 稼働中 → 停止中 → 名前順

ツールチップの強化

  • 稼働中の子エージェントのツールチップに 現在実行中のタスク名 を表示
  • タスク名は JSONL の tool_use(Agent) の input.description から取得
  • 経過時間も表示（「🔍探索 CLIオプション調査 — 2分30秒経過」）

セッション一覧（SessionTree）

変更内容 agentWatcher.isLive(sessionId) を使用（ロジックは同じだが呼び出し先が変わる）
enableAgentMonitor OFF 時は isLive() が常に false → 緑丸が出ない（修正）
表示は変更なし isLive: circle-filled + green / description に "● "
isPreviewing + isLive: target + green

6. CLIコマンドビルダー

cliBuilder.ts — CLIコマンド自動組み立てモジュール

新規作成 Phase 1c
目的CSMで設定した内容が実際のエージェント起動に確実に反映されるようにする。取締役が手動でオプションを覚える必要をなくす
関数buildCommand(config: AgentConfig): string
入力AgentConfig（session-manager.json から読み取った設定）
出力CLIコマンド文字列

生成されるコマンド例

# フル設定の例（opus / effort=max / thinking=ON / maxThinking=31999）
# ※ maxThinkingTokens は環境変数で指定（CLIフラグは存在しない）
# ※ --allowedTools はスペース区切りで複数指定
MAX_THINKING_TOKENS=31999 \
claude --resume 55f63fbc-6d5d-44aa-a188-1b5c16bcffa5 \
  --model opus \
  --effort max \
  --append-system-prompt "$(cat c:/xampp/Project/.agent-rules/CSM開発部.md)" \
  --allowedTools "Edit" "Write" "Bash" "Read" "Glob" "Grep" \
  --print

# 作業ディレクトリ指定の例（--add-dir で追加ディレクトリを指定）
# ※ --cwd は存在しない。--add-dir またはspawn時のcwdで対応
claude --resume 55f63fbc-... \
  --model sonnet \
  --effort high \
  --add-dir c:/xampp/Project/claude-session-manager \
  --append-system-prompt "$(cat c:/xampp/Project/.agent-rules/CSM開発部.md)" \
  --print

# 最小設定の例（haiku / effort未設定）
claude --resume abc12345-... \
  --model haiku \
  --append-system-prompt "$(cat ~/.claude/agent-rules/調査部.md)" \
  --print

組み立てロジック（疑似コード）

  1. env = {} — 環境変数の収集用
  2. parts = ['claude']
  3. config.sessionId がある場合: parts.push('--resume', config.sessionId)
  4. parts.push('--model', config.model) — 必須
  5. config.effort が設定されている場合: parts.push('--effort', config.effort)
        注意: 'max' は Opus 4.6 のみ対応。他モデルでは 'high' が上限
  6. config.thinkingEnabled === false の場合: CLIフラグは存在しない。settings.json の alwaysThinkingEnabled: false で制御するか、コメントで注記を出力
  7. config.thinkingEnabled !== false && config.maxThinkingTokens の場合: env.MAX_THINKING_TOKENS = String(config.maxThinkingTokens)
        （--max-thinking-tokens フラグは存在しない。環境変数 MAX_THINKING_TOKENS で制御）
  8. config.ruleFile が設定されている場合: parts.push('--append-system-prompt', `"$(cat ${config.ruleFile})"` )
  9. config.allowedTools?.length > 0 の場合: config.allowedTools.forEach(t => parts.push('--allowedTools', `"${t}"`))
        （スペース区切りで複数指定。例: --allowedTools "Edit" "Write" "Read"）
  10. config.workDir が設定されている場合: parts.push('--add-dir', config.workDir)
        （--cwd は存在しない。--add-dir で追加ディレクトリを指定、またはspawn時の cwd オプションで対応）
  11. parts.push('--print') — 非対話モード
  12. 環境変数プレフィックスを組み立て: envPrefix = Object.entries(env).map(([k,v]) => `${k}=${v}`).join(' ')
  13. return envPrefix ? `${envPrefix} ${parts.join(' ')}` : parts.join(' ')
CLI互換性 調査完了（2026-04-04）:
以下は公式ドキュメントおよび claude --help で確認済みの正確な情報:
  • --effort — 存在する。有効値: low / medium / high / max（max は Opus 4.6 のみ）
  • --max-thinking-tokens — 存在しない。環境変数 MAX_THINKING_TOKENS で制御
  • thinking 無効化 — CLIフラグなし。settings.json の alwaysThinkingEnabled またはキー操作（Alt+T）で制御
  • --append-system-prompt — 存在する。関連: --append-system-prompt-file（ファイル内容を追加）
  • --allowedTools — 存在する。スペース区切りで複数指定（例: --allowedTools "Edit" "Write" "Read"）
  • --cwd — 存在しない。代替: --add-dir（追加ディレクトリ指定）またはspawn時の cwd オプション
  • --resume — 存在する。短縮形 -r。セッションID/名前で再開
  • --print — 存在する。短縮形 -p。非対話モード
  • --verbose — 存在する。デバッグ用: --debug "api,mcp"

effort --effort {value} 設定時のみ low / medium / high / max の4段階。max は Opus 4.6 のみ対応
thinkingEnabled CLIフラグなし false の場合 settings.json の alwaysThinkingEnabled で制御。CLIに --no-thinking 等のフラグは存在しない
maxThinkingTokens 環境変数
MAX_THINKING_TOKENS={value}		 thinkingEnabled=true かつ設定時のみ --max-thinking-tokens フラグは存在しない。環境変数をコマンドの先頭に付与
ruleFile --append-system-prompt "$(cat {path})" 設定時のみ ルールファイルの内容をシステムプロンプトに追加。代替: --append-system-prompt-file {path}
allowedTools --allowedTools "Tool1" "Tool2" ... 設定時のみ スペース区切りで複数指定。ワイルドカード対応（例: "Bash(git *)"）
workDir --add-dir {workDir}
または spawn の cwd		 設定時のみ --cwd は存在しない。--add-dir で追加ディレクトリ指定、またはプロセス起動時の cwd で対応
（固定） --print 常時 非対話モード（パイプ起動）
Effort の 4段階（agent-settings-spec.html からの変更）:
agent-settings-spec.html では 3段階（low / medium / high）だったが、max を追加して4段階にする。
effort?: 'low' | 'medium' | 'high' | 'max'
low高速・低コスト簡単なタスク、ファイル検索
mediumバランス一般的な開発タスク
high精密・高品質複雑な設計、コードレビュー
max最大努力 ※ Opus 4.6 のみアーキテクチャ判断、仕様策定、取締役タスク
モデル制限: max は Opus 4.6 でのみ使用可能。Sonnet / Haiku では max を選択しても無効。
フォームUIでは、モデルが Opus 以外の場合に max カードをグレーアウトする。

## エージェント操作

### テスト部

```
  --model sonnet \
  --effort medium \
  --append-system-prompt "$(cat c:/xampp/Project/.agent-rules/テスト部.md)" \

```

### 調査部（使い捨て）
```
claude --model haiku \
  --append-system-prompt "$(cat ~/.claude/agent-rules/調査部.md)" \

```
※ 使い捨てモードのためセッションIDなし。--resume を付けないことで新規セッション起動
※ maxThinkingTokens は環境変数 MAX_THINKING_TOKENS で指定（CLIフラグなし）
※ Thinking無効化はCLIフラグが存在しないため、settings.json の alwaysThinkingEnabled で制御

自動更新のタイミング

  • エージェント設定の保存時（onSave コールバック内）
  • 取締役のルールファイルが存在する場合のみ更新
  • 「エージェント操作」セクション全体を再生成し、置換する
  • 手動で書き加えた内容がセクション外にあれば保持される

使い捨て（disposable）エージェントの扱い

  • sessionMode === 'disposable' の場合、--resume を付けない
  • 代わりにコメントで「※ 使い捨てモードのためセッションIDなし」を付記
  • プロンプトテキストは --print "指示内容" で渡す（取締役がメッセージを組み立てる）
再現性の保証:
このルールファイルにより、取締役は常に session-manager.json の最新設定を反映したコマンドを使用する。
設定変更 → ルールファイル自動更新 → 次回起動に即反映、というサイクルが回る。
