1. 概要

AgentWatcher は CSM の中核コンポーネントで、登録済みエージェントの稼働状態（Live / Idle）を リアルタイムに監視する。2つの独立した検出メカニズムを統合し、サイドバーのツリー表示に反映する。

検出方式 データソース 対象 タイミング
PIDベース ~/.claude/sessions/*.json 直接起動されたCLIセッション fs.watchイベント + 外部トリガー
シグナルベース ~/.claude/.csm-signals/*.json Hookで通知される子エージェント シグナルファイル作成イベント

4. PIDベース検出

データソース

Claude Code CLIは起動時に ~/.claude/sessions/{uuid}.json を作成する。 このファイルには sessionId、pid、cwd が含まれる。

検出ロジック（update() 内）

  1. sessions/ ディレクトリの全 .json ファイルを並列読取
  2. 各ファイルをJSONパースし、data.sessionId と data.pid を取得
  3. process.kill(pid, 0) でプロセス生存確認（シグナル0 = 存在確認のみ）
  4. 生存 → newLiveSessionIds に追加、cwd・mtimeを記録
  5. 死亡 → ゾンビJSONファイルを ~/.claude/.trash/ に移動
  6. 全ファイル処理後、this.liveSessionIds = newLiveSessionIds で差替
注意: PIDベース検出は liveSessionIds を毎回 完全に再構築 する。 前回の状態は引き継がない。これにより、プロセス終了を確実に検出できる。

ゾンビJSON処理

PID死亡済みのsessions/*.jsonは ~/.claude/.trash/ に移動（rm禁止ルール準拠）。 ファイル名にタイムスタンプを付与して衝突を防ぐ。

5. シグナルベース検出

データソース

CSMのHookシステム（settings.jsonの hooks.SessionStart / hooks.SubagentStop 等）が ~/.claude/.csm-signals/ にJSONファイルを書き込む。

シグナルファイル形式

interface SignalData {
  type: 'start' | 'stop';
  timestamp: string;
  pid?: number;
  cwd?: string;
  sessionId?: string;
  agentType?: string;
  description?: string;
  parentSessionId?: string;
}

処理フロー（processSignals()）

  1. .csm-signals/ の全 .json ファイルを列挙
  2. 各ファイルを読取・パース
  3. type === 'start' → signalLiveSessions.set(sessionId, true)
  4. type === 'stop' → signalLiveSessions.set(sessionId, false)
  5. 処理済みシグナルファイルを unlink で削除
  6. 変更があれば applySignalState() + _onDidChange.fire()
デバウンス: シグナル処理は200msのデバウンス付き。短時間に複数のstart/stopが来ても 一度にまとめて処理される。

6. applySignalState() 詳細

applySignalState() は signalLiveSessions の内容を liveSessionIds に反映するブリッジ関数。2つのパスで呼ばれる:

呼び出し元タイミング
update()PIDベーススキャン完了後（liveSessionIds再構築直後）
processSignals()新しいシグナルファイル処理後

実装コード（v0.3.1 修正後）

private applySignalState(): void {
  // パス1: signalLiveSessionsの内容をliveSessionIdsに反映
  for (const [sessionId, isLive] of this.signalLiveSessions) {
    if (isLive) {
      // startシグナル: PIDベースで未検出ならシグナルを信頼して追加
      if (!this.liveSessionIds.has(sessionId)) {
        this.liveSessionIds.add(sessionId);
      }
    } else {
      // stopシグナル: liveSessionIdsから確実に削除
      this.liveSessionIds.delete(sessionId);
      // 処理済みstopエントリを除去（メモリリーク防止）
      this.signalLiveSessions.delete(sessionId);
    }
  }

  // パス2: PIDベースで確認済みのstartシグナルをクリーンアップ
  for (const [sessionId] of this.signalLiveSessions) {
    if (this.liveSessionIds.has(sessionId)) {
      this.signalLiveSessions.delete(sessionId);
    }
  }
}

パス1: メイン反映ループ

条件アクション理由
isLive === true かつ PID未検出 liveSessionIds.add() Hookシグナルの方がPIDスキャンより先に届く場合がある。シグナルを信頼して即座にLive扱い
isLive === true かつ PID検出済み 何もしない 既にliveSessionIdsに含まれている。パス2で signalLiveSessions からクリーンアップ
isLive === false liveSessionIds.delete() + signalLiveSessions.delete() stopシグナルは最優先。PID生存中でもstopシグナルがあれば停止扱い。処理後エントリ除去

パス2: クリーンアップループ

パス1で残った signalLiveSessions のエントリ（isLive === true のみ）について、 liveSessionIds に既に含まれていれば不要なので削除。 これにより、PIDベースの定期スキャンで確認済みのセッションはシグナル追跡から外れる。

設計意図: signalLiveSessionsは「PIDベースで検出できない過渡期のセッション」を一時的に補完するバッファ。 PIDベースで確認されるか、stopシグナルが来れば役目を終えてクリーンアップされる。

7. PID vs シグナルの優先順位

状況PIDシグナル結果理由
通常稼働 ✅ 生存 start Live 両方一致。signalLiveSessionsからクリーンアップ
起動直後（PID未検出） ❌ 未検出 start Live シグナルを信頼。次回PIDスキャンで引き継がれる
終了直後（PID残留） ✅ 生存 stop Idle stopシグナルが最優先。liveSessionIdsから強制削除
PID死亡 ❌ 死亡 なし Idle PIDスキャンでliveSessionIdsに含まれない
シグナル未到達 ✅ 生存 なし Live PIDベースで検出。シグナルは補助的
重要: stopシグナルはPIDベースの結果を上書きする。これにより、プロセスが残留していても Hook通知でセッション終了を即座に反映できる。ただし、次回のPIDスキャンでPIDが生存していれば再度Liveに戻る 可能性がある（stopシグナルは処理後にsignalLiveSessionsから除去されるため）。

9. 再スキャントリガー

トリガー経路実行される処理
fs.watch sessions/ scheduleUpdate() → update() PIDスキャン全体 + applySignalState + states構築
fs.watch .csm-signals/ scheduleSignalProcessing() → processSignals() シグナル処理 + applySignalState（liveSessionIdsへの差分反映のみ）
refreshAll() agentWatcher.scheduleUpdate() PIDスキャン全体（エージェント登録・編集・削除時）
child.on("close") agentWatcher.scheduleUpdate() PIDスキャン全体（createSessionForAgent完了時）

refreshAll() 経由のトリガー

v0.3.1で追加。以下のコマンドが refreshAll() を呼び、間接的にPIDスキャンが走る:

  • claudeManager.addAgent（エージェント追加）
  • claudeManager.editAgent（エージェント編集）
  • claudeManager.deleteAgent（エージェント削除）
  • claudeManager.registerAgent（セッションからエージェント登録）
  • claudeManager.renewSession（セッション更新）
  • その他全てのUI操作でrefreshAll()が呼ばれる場面

child.on("close") 経由のトリガー

v0.3.1で追加。createSessionForAgent() でspawnしたCLIプロセスが終了した際に agentWatcher.scheduleUpdate() を呼ぶ。これにより、セッション初期化完了後に プロセスの死亡を即座に検出し、稼働状態を正しくIdleに戻す。

10. 状態遷移

エージェント状態の定義

interface AgentWatcherState {
  agentName: string;          // エージェント名
  sessionId: string;          // 紐づけされたセッションID
  isLive: boolean;            // 稼働中か否か
  activeSubagentIds: string[]; // 実行中のサブエージェントtoolUseId一覧
}

isLive の決定ロジック

const isLive = agent.sessionId
  ? this.liveSessionIds.has(agent.sessionId)
  : false;

sessionId が空のエージェントは常に isLive: false。

11. ツリー表示への反映

通知チェーン

  1. update() or processSignals() が状態変更を検出
  2. _onDidChange.fire() でイベント発火
  3. extension.ts の agentWatcher.onDidChange() コールバックが受信
  4. agentProvider.refresh() → ツリー再描画
  5. sessionProvider.setLiveSessionIds() → セッション一覧のバッジ更新

変更検出（hasChanged）

前回の states マップと比較し、以下のいずれかが変わった場合のみイベント発火:

  • エージェント数の変化
  • isLive の変化
  • sessionId の変化
  • activeSubagentIds の変化（長さ or 要素）

12. エッジケース

#シナリオ挙動評価
E-1 startシグナル後、PIDが即死亡
（CLIクラッシュ等）		 startシグナルでLive化 → 次回PIDスキャンでPID死亡検出 → Idleに戻る。signalLiveSessionsのstartエントリはパス2でPID未検出のため残留するが、liveSessionIdsには含まれないため表示上は正しくIdle ✅ 正常
E-2 stopシグナル後、同じsessionIdで再度startシグナル stopで signalLiveSessions.delete() 済み → 新startで set(id, true) → 再びLive化 ✅ 正常
E-3 sessions/*.jsonが存在しない
（初回起動）		 readdir が空 → liveSessionIds空 → 全エージェントIdle ✅ 正常
E-4 二重実行（高頻度トリガー） this.updating フラグで updateAsync() の二重実行を防止 ✅ 正常
E-5 signalLiveSessionsのメモリリーク startエントリ: PID確認済みでパス2削除。stopエントリ: パス1で即座に削除。蓄積しない ✅ 正常
E-6 stopシグナルがstart前に到着
（順序逆転）		 stopで set(id, false) → applySignalStateでliveSessionIdsから削除 + signalLiveSessions削除。後続startは新規エントリとして正常に処理 ✅ 正常
E-7 PID生存中にstopシグナル → 次回PIDスキャン stopでliveSessionIdsから削除・signalLiveSessions削除 → 次回PIDスキャンでPID生存を検出 → 再びliveSessionIdsに追加される → Live復帰 ⚠️ 注意
（後述）
E-8 createSessionForAgent完了時のクリーンアップ child.on("close") → scheduleUpdate() → PIDスキャンで初期化プロセスの死亡を検出 → Idle化 ✅ 正常

E-7 の詳細分析

⚠️ エッジケース E-7: stopシグナルでIdleにしても、次回PIDスキャン（300msデバウンス後）で PIDがまだ生存していれば再びLiveに復帰する。

影響: 実運用上は問題にならない。stopシグナルが送られるのはHookの SubagentStop イベント時で、 この時点でCLIプロセスは終了処理中。300msのデバウンス後にはPIDも死亡しているのが通常。 万が一PIDが残留していても、数秒後のゾンビJSON処理で最終的にIdleに戻る。

根本対策（将来）: stopシグナルのsessionIdを「永続ブラックリスト」に入れ、PIDスキャンでも 無視する方式が考えられるが、現状の挙動で実用上の問題は無い。

13. コードレビュー結果

変更箇所の評価

変更コード評価
stopシグナル時にliveSessionIdsからdelete this.liveSessionIds.delete(sessionId) ✅ 正しい — 修正前はstopシグナルがliveSessionIdsに反映されず、稼働状態がリセットされなかった
処理済みstopをsignalLiveSessionsから除去 this.signalLiveSessions.delete(sessionId) ✅ 正しい — メモリリーク防止。stopは一度処理すれば不要

Map iteration中のdelete安全性

安全: JavaScriptの Map.prototype.forEach / for...of は イテレーション中の delete を仕様上許容している（MDN: "A Map object iterates entries in insertion order. A for...of loop returns an array of [key, value] for each iteration. Deletion of entries during iteration is safe."）。 パス1・パス2ともに安全。
