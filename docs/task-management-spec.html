1. 背景と課題

取締役がエージェントにタスクを委任した後、以下の運用上の問題が発生している：

課題影響頻度
完了を自分で確認しに行くしかない取締役の時間を浪費、応答遅延毎回
エラーや権限要求で止まっても気づけないタスク停滞、デッドロック週数回
VS Code再起動でプロセスが死んでも分からない進行中タスクが消失月数回
「何を投げてたっけ」が分からなくなるコンテキスト消失で再着手困難毎回（セッション切替時）
設計方針: 既存の AgentWatcher のイベント駆動アーキテクチャを拡張し、 新たなポーリングループを追加しない。CPU負荷の増加を最小限に抑える。

2. 機能概要

3つの機能を段階的に追加する：

#機能概要依存
1 タスクログ エージェントにタスクを投げた記録を永続化。誰に・何を・いつ・出力先を記録 dataStore.ts
2 状態検知 タスクの状態（実行中・完了・停止・エラー）を自動判定 AgentWatcher, subagentDetector
3 通知 状態変化時にVS Code通知 + ステータスバー更新 機能1 + 機能2

3. アーキテクチャ

3.1 全体構成図

+-------------------------------------------------------------+ | extension.ts | | | | agentWatcher.onDidChange --> taskTracker.evaluate() | | | | | +------+------+ | | | TaskTracker | | | | (新規) | | | +------+------+ | | | | | +----------------------+------------------+ | | | | | | | v v v | | +-------------+ +----------------+ +------------+ | | | dataStore | | AgentWatcher | | Notifier | | | | (taskLogs[]) | | (PID + mtime) | | (VS Code) | | | +-------------+ +----------------+ +------------+ | | | | +---------------------------------------------+ | | | agentTreeProvider (TaskLogItem 子要素追加) | | | +---------------------------------------------+ | +-------------------------------------------------------------+

3.2 設計原則

  • 既存のAgentWatcherに乗る: 新たなポーリングループを作らない。AgentWatcher の onDidChange イベントをフックして状態を評価する
  • enableAgentMonitor OFF でもタスクログは保持: ログの記録と閲覧は監視機能に依存しない。状態検知と通知のみ監視に依存する
  • データは session-manager.json に格納: 新規ファイルを作らず、既存のManagerDataに taskLogs[] を追加
  • 上限付き: taskLogs は最大100件（古いものから自動削除）。メモリリーク防止
  • バッチ保存: evaluate() 内で全タスク評価後、変更があった場合のみ1回だけ saveData() を呼ぶ（品質管理部H-3対応）

4. 機能1: タスクログ

4.1 記録タイミング

タスクログは以下の2つの方法で記録される：

方法トリガー詳細
A. 手動登録 エージェントツリーのコンテキストメニュー「タスクを記録」 ユーザーがタスク概要・出力先ファイルを入力して登録
B. 自動検出 AgentWatcher が JSONL を解析した際 subagentDetector が新しい Task/Agent tool_use を検出したとき、自動でタスクログに追加

A. 手動登録フロー

// コンテキストメニュー「タスクを記録」-> QuickInput
1. タスク概要を入力（必須、最大200文字 — dataStore側で.slice(0,200)）
2. 出力先ファイルを入力（任意 — ワークスペース配下のみ許可）
3. TaskLog レコードを作成し dataStore に保存

B. 自動検出フロー

// AgentWatcher.update() -> subagentDetector.detectSubagents()
// 新しい toolUseId が検出されたら自動でタスクログに追加
1. agentWatcher.onDidChange が発火
2. TaskTracker が前回の activeSubagentIds と比較
3. 新規の toolUseId があれば TaskLog を自動生成

   - summary: SubagentInfo.description（tool_use の description/prompt）
   - outputFile: undefined（手動で設定可能）
4. toolUseId が消えたら（tool_result が来た）完了とマーク

5. 機能2: 状態検知

5.1 状態遷移図

+----------+ 登録 ------>| pending | | (待機中) | +----+-----+ | PIDがライブになった v +----------+ | running |<------+ | (実行中) | | JSONL更新再開 +--+---+---+ | | | | PID消失 -----+ | +------+-----+ or tool_result | | stalled | | | (停止疑い) | +----------------+ +------------+ | JSONL更新が ^ | 60秒以上停止 | | かつPID生存 ---------------+ v +----------+ +----------+ |completed | | error | | (完了) | | (エラー) | +----------+ +----------+ ^ ^ | | tool_result PID異常終了 or PID正常終了

5.2 状態判定ロジック

TaskTracker は AgentWatcher の onDidChange イベント発火時に、各タスクログの状態を評価する。 新しいポーリングループは作らない。

状態判定条件アイコン
pending タスクログ登録直後。対応するエージェントのPIDがまだ生存していない $(circle-outline) グレー
running 対応エージェントのPIDが生存 AND JSONL mtime が60秒以内 $(sync~spin) 緑
stalled PID生存 BUT JSONL mtime が60秒以上更新なし（権限待ち・入力待ち等） $(warning) 黄
completed tool_result を受信 OR PIDが正常終了 OR 手動完了マーク $(check) 緑
error PIDが異常終了 $(error) 赤

5.3 stalled 判定の詳細

パフォーマンス注意: stalled 判定のためにJSONL末尾を毎回読むのはコストが高い。 AgentWatcher の update() 内で取得する JSONL ファイルの mtime を活用する。

stalled 判定ロジック:

function evaluateStalled(taskLog: TaskLog, agentWatcher: AgentWatcher): boolean {
  // AgentWatcher.update() で取得・キャッシュした mtime を参照（追加 I/O なし）
  // ※ sessionMtimes Map は Phase B で agentWatcher.ts に追加実装する（H-1対応）
  const mtime = agentWatcher.getSessionMtime(taskLog.sessionId);
  if (mtime === undefined) { return false; }
  const now = Date.now();
  const threshold = config.get('taskStalledThreshold', 60) * 1000; // デフォルト60秒
  return (now - mtime) > threshold;
}
品質管理部指摘 H-1 対応: 現在の agentWatcher.ts には sessionMtimes Map が存在しない。 Phase B の実装タスクとして「agentWatcher.ts に sessionMtimes Map を追加」を明示的に含める。 update() 内で sessions/*.json から sessionId を取得する際に、 対応する JSONL ファイルの fs.statSync の mtime も取得し Map にキャッシュする。
品質管理部指摘 M-1 対応: stalled 閾値を 30秒 -> 60秒 に変更。Extended Thinking（最大31,999トークン）使用時に 30秒以上の無応答が発生するため。設定 taskStalledThreshold の最小値は10秒。

5.4 エラー検出方式

品質管理部指摘 M-2 対応: outputFile 末尾の内容解析によるエラー検出は廃止。偽陽性（error handling, class CustomError 等の正常文字列の誤検出）リスクが高いため。 エラー判定はPIDの終了状態のみに限定する。

エラー検出はPID終了コードに一本化：

  • PID消失 + completed でない: error と判定
  • outputFile の内容解析は行わない（シンプルで安全）
  • 出力先ファイルの mtime 監視のみ残す（完了判定の補助として）

5.5 outputFile パスバリデーション

品質管理部指摘 H-2 対応（OWASP A01:2021 Broken Access Control）: outputFile に任意パスを指定可能な場合、パストラバーサルやUNCパスのリスクがある。 以下のバリデーションを必須とする。 
function validateOutputFile(filePath: string): boolean {
  if (!filePath) { return false; }
  if (filePath.length > 500) { return false; }

  const resolved = path.resolve(filePath);

  // UNCパス拒否
  if (resolved.startsWith('\\\\')) { return false; }

  // ワークスペース配下のみ許可
  const workspaceRoot = vscode.workspace.workspaceFolders?.[0]?.uri.fsPath;
  if (!workspaceRoot) { return false; }
  return resolved.startsWith(path.resolve(workspaceRoot));
}

7. データモデル

7.1 TaskLog 型定義

// types.ts に追加
export interface TaskLog {
  id: string;               // ユニークID（Date.now().toString(36) + Math.random()）
  agentName: string;        // エージェント名（例: CSM開発部）
  sessionId: string;        // エージェントのセッションID
  summary: string;          // タスク概要（最大200文字、dataStore側で切り詰め）
  outputFile?: string;      // 出力先ファイルパス（ワークスペース配下のみ許可）
  status: TaskStatus;       // 現在の状態
  createdAt: number;        // 作成タイムスタンプ（ms）
  completedAt?: number;     // 完了タイムスタンプ（ms）
  toolUseId?: string;       // 自動検出時の tool_use ID（手動登録時は undefined）
  notifiedStatus?: TaskStatus; // 最後に通知した状態（重複通知防止）
  lastNotifiedAt?: number;  // 最後に通知した時刻（フラッピング対策、60秒間隔制限）
}

export type TaskStatus = 'pending' | 'running' | 'stalled' | 'completed' | 'error';
品質管理部指摘 M-4 対応: crypto.randomUUID() は Node.js バージョン依存のため、 Date.now().toString(36) + Math.random().toString(36).slice(2) で代替。
品質管理部指摘 M-2 対応: errorHint フィールドを廃止。エラー検出がPID終了コードのみに限定されたため不要。

新しいビューは追加しない。既存のエージェント管理ビューにインラインで表示する。

9. 設定項目

設定キー型デフォルト説明
claudeManager.taskNotification boolean true タスク完了・エラー時のVS Code通知を有効にする
claudeManager.taskStalledThreshold number 60 stalled 判定の閾値（秒、最小10）。Extended Thinking 対応で60秒推奨
claudeManager.taskAutoCleanupHours number 72 完了/エラーのタスクログを自動削除するまでの時間（時間）。running/stalled/pending は168時間

enableAgentMonitor との関係:
  • enableAgentMonitor: true -> タスクログ OK / 状態検知 OK / 通知 OK
  • enableAgentMonitor: false -> タスクログ OK / 状態検知 NG / 通知 NG
監視OFFでもタスクログの記録・閲覧は可能。ただし状態は自動更新されず pending のまま。 手動で「完了にする」操作のみ可能。
品質管理部指摘 H-4 対応: enableAgentMonitor が ON -> OFF に切り替わったタイミングで、 running/stalled 状態のタスクを pending にリセットし、 ユーザーに「監視がOFFになりました。進行中のタスクは手動で完了にしてください」と通知する。 加えて、running/stalled/pending で168時間経過したタスクも自動クリーンアップ対象とする。

11. パフォーマンス設計

11.1 CPU負荷分析

処理頻度コスト対策
TaskTracker.evaluate() AgentWatcher.onDidChange 時
(5秒間隔 + fs.watch)		 低: O(taskLogs.length) の配列走査 taskLogs は最大100件なので問題なし
outputFile の mtime チェック 同上 低: fs.statSync 1回/ファイル outputFile 設定済みタスクのみ（通常1~3件）
dataStore 保存 evaluate()で変更があった時のみ（バッチ） 低: 1回のみの JSON.stringify + writeFileSync バッチ保存で連続I/Oを防止（H-3対応）

11.2 追加I/Oの最小化

設計の鍵: TaskTracker は自前でファイルI/Oを行わない。 AgentWatcher が既に取得している情報（PID状態、セッションファイルmtime）を受け取るだけ。 
// AgentWatcher.update() の拡張（Phase B で実装）
// sessions/*.json を読むループ内で JSONL ファイルの mtime も取得

private sessionMtimes = new Map<string, number>();

// update() 冒頭で clear、ループ内で再構築
update(): void {
  this.sessionMtimes.clear(); // M-3対応: 毎回クリアして再構築

  // 既存の sessions/*.json 読み込みループ内:
  // sessionId を取得した後、対応する JSONL ファイルの stat を取得
  // this.sessionMtimes.set(sessionId, jsonlStat.mtimeMs);
}

// 外部API:
getSessionMtime(sessionId: string): number | undefined {
  return this.sessionMtimes.get(sessionId);
}

11.4 parseSessionQuick との整合性

整合性確認:

12. 品質管理部レビュー結果と対応

高重要度（全4件 -> 全件対応済み）

ID指摘対応
H-1 fs.statSync が「キャッシュ済み」は誤り。現時点で agentWatcher に sessionMtimes は存在しない コメントを修正。Phase B の実装タスクに sessionMtimes Map 追加を明記
H-2 outputFile のパストラバーサル（OWASP A01:2021）。UNCパス・ワークスペース外パスを拒否すべき validateOutputFile() を追加。ワークスペース配下のみ許可、UNCパス拒否。Section 5.5 に明記
H-3 saveData() の連続呼び出しで同期I/O集中。10件同時変更時に10回 writeFileSync evaluate() 内でバッチ処理。全タスク評価後、変更があった場合のみ1回だけ saveData() を呼ぶ
H-4 監視ON時のタスクが監視OFF後に永久残留（running/stalled が自動クリーンアップ対象外） OFF切替時に running/stalled を pending にリセット + 通知。running/stalled/pending の168時間自動クリーンアップ追加

中重要度（全5件 -> 全件対応済み）

ID指摘対応
