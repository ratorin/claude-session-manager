1. 部署名

部署名

必須 テキスト入力
説明エージェントの識別名。組織図・ツリー・ステータスバー等あらゆる箇所で使用される
AgentConfigname: string
デフォルト空文字（プレースホルダー: 「CSM開発部」）
バリデーション空文字不可。保存ボタンは部署名が空の間は disabled
一意性dataStore.addAgent() は name をキーとして upsert する。同名の場合は上書き
CLI反映なし（CLIオプションには渡さない）。ルールファイル内に記述される

挙動の詳細

  • 入力するたびに updateRuleFilePath() が呼ばれ、ルールファイルパスのプレビューが更新される
  • 保存時、ルールファイルのファイル名は {name}.md となる
  • 編集時に名前を変更した場合、旧名の AgentConfig は removeAgent(oldName) で削除後、新名で追加
  • 取締役プリセットでは "取締役" がデフォルト値として入る

役割の説明

AgentConfigrole: string

バリデーションなし（空でも保存可能）

  • プレビュー（agentPreviewPanel）のバッジに表示
  • 親エージェント選択肢のラベルにも {name} — {role} として表示

3. モデル選択

モデル選択

必須 カード型ラジオ
説明エージェントが使用する Claude モデルを選択。後続の Effort / Thinking / maxThinkingTokens の有効/無効にも影響する
AgentConfigmodel: 'opus' | 'sonnet' | 'haiku'
デフォルト'opus'（新規作成時・取締役プリセット共通）
バリデーション3択のラジオのため常に1つ選択状態
CLI反映claude --model {model} — 取締役が子エージェントをCLI起動する際に使用
選択肢説明文推奨用途
opus高度な判断・複雑な開発取締役、複雑な開発部署
sonnet定型作業・補助（コスト効率◎）日常的な開発作業
haiku軽量タスク・高速応答調査、軽量タスク

挙動の詳細

  • エージェント一覧で [opus] のようにモデルバッジとして表示
  • セッション一覧では先頭にモデル頭文字（Ｏ/Ｓ/Ｈ）を表示
  • 組織図のカード内にモデルバッジ表示
  • モデル変更時、後続の Effort / Thinking / maxThinkingTokens の有効/無効状態を連動更新する（詳細は #11 モデル別機能対応表 を参照）

4. Effort（推論努力レベル）

Effort

任意 カード型ラジオ Phase 1b 計画
説明モデルの推論にかける労力を制御する。低いほど高速・低コスト、高いほど精密・高コスト
AgentConfigeffort?: 'low' | 'medium' | 'high' | 'max'（追加予定）
デフォルト'high'
バリデーション4択のラジオのため常に1つ選択状態。モデルが非対応の場合はグレーアウト。max は Opus 4.6 のみ対応 — 他モデルでは max カードをグレーアウト
CLI反映claude --effort {value}
フォーム配置モデル選択（#3）の直後
選択肢説明文推奨用途
low高速・低コスト簡単なタスク、定型作業、ファイル検索・読み取り
mediumバランス一般的な開発タスク、コードレビュー
high精密・高品質複雑な設計、アーキテクチャ判断
max最大努力 ※ Opus 4.6 のみ仕様策定、取締役タスク、最高精度が必要な場面
Low
高速・低コスト
Medium
バランス
High
精密・高品質
Max
最大努力（Opus限定）

想定挙動

  • モデル選択と同じカード型ラジオUIを使用（統一感のあるデザイン）
  • モデルが Effort 非対応の場合、4枚とも opacity: 0.35 + pointer-events: none でグレーアウト
  • max は Opus 4.6 のみ対応。Sonnet / Haiku 選択時は max カードのみグレーアウト（low/medium/high は有効）
  • グレーアウト時は「このモデルでは使用できません」のテキストを表示
  • Effort は Thinking とは独立した設定（Thinking OFF でも Effort は機能する）
  • 取締役ルールファイルの「エージェント操作」セクションで --effort {value} を記載

5. Thinking ON/OFF

Thinking ON/OFF

任意 トグルスイッチ Phase 1b 計画
説明エージェントの Extended Thinking（拡張思考）を有効/無効にする
AgentConfigthinkingEnabled?: boolean（追加予定）
デフォルトtrue（Claude Code のデフォルト動作に合わせる）
バリデーションboolean のトグル。モデルが非対応の場合はグレーアウト（OFF固定）
CLI反映 CLIフラグは存在しない（--no-thinking 等は非対応）。
制御方法: ~/.claude/settings.json の alwaysThinkingEnabled を変更、
または対話モードで Alt+T（Windows/Linux）/ Option+T（macOS）で切り替え。
ON の場合: 追加対応なし（デフォルト動作）
フォーム配置Effort（#4）の直後

想定挙動

  • ON/OFFのトグルスイッチで直感的に切り替え
  • OFFにすると後続の maxThinkingTokens（#6）を自動的にグレーアウト
  • モデルが Thinking 非対応（例: Haiku）の場合、トグル自体がグレーアウト（OFF固定）し、maxThinkingTokens もグレーアウト
  • 軽量タスク（調査、単純なコード生成）では OFF にしてコスト削減
  • 取締役や複雑な判断が必要なエージェントは ON を推奨
  • 取締役ルールファイルの「エージェント操作」セクションに thinking 制御方法（settings.json の alwaysThinkingEnabled）を注記
グレーアウト条件: モデルが Thinking 非対応 → トグルは OFF 固定 + グレーアウト。 ユーザーが操作不能であることを明示するため、「Haiku は Extended Thinking に非対応です」等のテキストを表示する。

6. maxThinkingTokens

maxThinkingTokens

任意 数値入力 Phase 1b 計画
説明Extended Thinking に割り当てる最大トークン数。大きいほど深く考えるがコストが増加
AgentConfigmaxThinkingTokens?: number（追加予定）
デフォルト31999
バリデーション最小: 1,024 / 最大: 128,000（モデルにより上限が異なる）
有効条件thinkingEnabled === true かつ モデルが Thinking 対応の場合のみ有効
CLI反映CLIフラグは存在しない。環境変数 MAX_THINKING_TOKENS={value} をコマンドの先頭に付与して制御。
例: MAX_THINKING_TOKENS=31999 claude --resume {id} --model opus --print
フォーム配置Thinking ON/OFF（#5）の直後

想定挙動

  • 数値入力フィールド（テキストボックス、type="number"）
  • Thinking OFF 時 または モデルが Thinking 非対応時は入力フィールド全体がグレーアウト
  • コスト目安の注釈を表示（「※ 値が大きいほど応答が遅く、コストが高くなります」）
  • 取締役ルールファイルの「エージェント操作」セクションに環境変数 MAX_THINKING_TOKENS の使い方を追記
  • 未入力（空欄）の場合は undefined として保存 → CLI側のデフォルトに従う

7. セッション運用

セッション運用

必須 カード型ラジオ
説明セッションの使い方を制御する。固定は同じセッションを継続、使い捨てはタスクごとに新規
AgentConfigsessionMode?: 'fixed' | 'disposable'
デフォルト'fixed'
バリデーション2択のラジオのため常に1つ選択状態
CLI反映なし（CSM内部でのセッション管理方針のみ）
選択肢説明文動作
fixed同じセッションを継続使用（推奨）1つのセッションIDに紐づけ。コンテキストが蓄積される
disposableタスクごとに新しいセッション「使い捨て」ラベルがUI各所に表示

挙動の詳細

  • エージェント一覧で disposable の場合「使い捨て」ラベルを表示
  • 「セッションを新しくする」コマンドは運用モードに関係なく使用可能
  • 使い捨てモードでもセッションの紐づけ自体は同じ仕組み
  • 注意: セッション運用モードはガイドラインに過ぎず、CSMが自動でセッション作成・破棄を行うわけではない

8. 親エージェント

親エージェント

任意 セレクトボックス
説明階層構造を構築するための上位エージェント指定
AgentConfigparentAgent?: string（親エージェントの部署名）
デフォルトundefined（「なし（トップレベル）」が選択状態）
バリデーション自分自身は選択肢から除外（filter(a => a.name !== existing?.name)）
CLI反映なし。ルールファイルに - 報告先: {parentAgent}（親エージェント） として記載

挙動の詳細

  • 選択肢は dataStore.getAgents() から動的に生成。表示形式: {name} — {role}
  • 親を設定すると、エージェント一覧ツリーで親ノード配下に子として表示される
  • 組織図でも親子関係に基づいて階層レイアウトされる
  • ルールファイル自動生成時に - 報告先: {parentAgent}（親エージェント）。作業完了時は結果を報告すること が追記される
  • 循環参照のチェックは現在未実装（A→B→A のような設定が可能）

9. 作業フォルダ

作業フォルダ

任意 テキスト + フォルダ選択
説明エージェントの作業ディレクトリ（cwd）。ルールファイルにフォルダ制限としても反映
AgentConfigworkDir?: string
デフォルトundefined（空文字）
バリデーションなし（パスの存在チェックは行わない）
CLI反映--cwd は存在しない。代替: --add-dir {workDir} で追加ディレクトリを指定、またはプロセス起動時の cwd オプションで対応（ルールファイルに記載）

挙動の詳細

  • 「選択」ボタンで vscode.window.showOpenDialog（フォルダ選択）が開く
  • 選択結果は postMessage({ type: 'folderSelected' }) でフォームに反映
  • 手動入力も可能（パスのバリデーションなし）
  • 自動生成ルールファイルに - 編集対象は `{workDir}` 内のみ。それ以外のフォルダは絶対に変更しない が追記される（v0.2.8〜）
  • 注意書き: 「※ エージェントのcwd（作業ディレクトリ）になります。ルールファイルの編集対象フォルダ制限にも使用されます。」

10. ルールファイルのスコープ

ルールファイルのスコープ

必須 カード型ラジオ v0.2.8 新規
説明ルールファイルの保存先を制御する。プロジェクト固有かグローバル共通かを選択
AgentConfigscope?: 'global' | 'project'
デフォルト'project'
バリデーション2択のラジオのため常に1つ選択状態
CLI反映なし（ルールファイルの配置先のみに影響）
選択肢フォルダ用途
project{workspace}/.agent-rules/プロジェクト固有のルール
global~/.claude/agent-rules/全プロジェクト共通のルール

挙動の詳細

  • 部署名・スコープ変更のたびに updateRuleFilePath() が呼ばれ、生成先パスをリアルタイムプレビュー
  • ラジオのサブテキストに実際のフォルダパスを表示
  • 保存時、ruleFile が未設定の場合に autoGenerateRuleFile(config) が呼ばれ、scope に基づくフォルダにファイルを生成
  • 既にルールファイルが設定済みの場合（編集時）、スコープ変更してもルールファイルパスは変わらない
  • 他スコープに同名ファイルが存在する場合、警告ダイアログを表示
フォーム入力 → scope + name を決定
↓
保存ボタン → getFormData() で scope を含む config を送信
↓
extension.ts → autoGenerateRuleFile(config)
    ├ ruleFile あり → スキップ（既存を維持）
    ├ ファイル存在 → 紐づけのみ（上書きしない）
    └ ファイルなし → テンプレートから自動生成
↓
dataStore.addAgent() → session-manager.json に保存

11. モデル別機能対応表

モデル × 設定項目の対応マトリクス

Phase 1b 計画
モデル Effort
--effort		 Effort max Thinking ON/OFF
（settings.json制御）		 maxThinkingTokens
（環境変数 MAX_THINKING_TOKENS）
Opus ✓ 有効（low/medium/high/max） ✓ 有効 ✓ 有効 ✓ 有効
Sonnet ✓ 有効（low/medium/high） ✗ グレーアウト（Opus限定） ✓ 有効 ✓ 有効
Haiku ✓ 有効（low/medium/high） ✗ グレーアウト（Opus限定） ✗ グレーアウト（非対応） ✗ グレーアウト（非対応）

グレーアウトの実装仕様

  • モデル変更時に onModelChange() を呼び出し、各項目の有効/無効を動的に切り替える
  • グレーアウト表現: opacity: 0.35 + pointer-events: none を適用
  • グレーアウト中の項目には「このモデルでは使用できません」のテキストを表示
  • グレーアウト中の値は undefined として保存（CLIオプションを付与しない）
  • モデルを変更して再度有効になった場合、前回の値を復元する（localStorageやhidden fieldで保持）
連動ルール:
1. モデル変更 → Effort（max制限） / Thinking / maxThinkingTokens の有効/無効を更新
2. モデルが Opus 以外 → Effort の max カードをグレーアウト（low/medium/high は有効）
3. Thinking OFF → maxThinkingTokens をグレーアウト
4. モデルが Thinking 非対応 → Thinking を OFF 固定 + グレーアウト → maxThinkingTokens もグレーアウト

つまり maxThinkingTokens が有効になる条件は: モデルが Thinking 対応 AND Thinking が ON

CLI反映の注意:
• Thinking ON/OFF: --no-thinking 等のCLIフラグは存在しない。settings.json で制御
• maxThinkingTokens: --max-thinking-tokens フラグは存在しない。環境変数 MAX_THINKING_TOKENS で制御

UIの状態遷移

Opus 選択時:
  Effort → 全4択有効（low/medium/high/max 選択可）
  Thinking → 有効（ON/OFF 切替可）※制御は settings.json 経由
  maxThinkingTokens → Thinking ON なら有効、OFF ならグレー ※環境変数 MAX_THINKING_TOKENS

Sonnet 選択時:
  Effort → low/medium/high 有効、max はグレーアウト（Opus限定）
  Thinking → 有効（ON/OFF 切替可）※制御は settings.json 経由
  maxThinkingTokens → Thinking ON なら有効、OFF ならグレー

Haiku 選択時:
  Effort → low/medium/high 有効、max はグレーアウト（Opus限定）
  Thinking → グレーアウト（OFF固定）「Haiku は Extended Thinking に非対応です」
  maxThinkingTokens → グレーアウト
