# レポート: エージェント紐づけ後の役割認識問題

**日付**: 2026-04-17
**報告者**: Curtain_leader セッション
**対象**: CSM開発チーム

## 問題の概要

CSMでセッションをエージェントに紐づけた後、そのセッション内のClaudeが**自分の役割を自動認識しない**。ユーザーが「あなたの役割を確認」と聞いても、エージェント定義の内容を把握していなかった。

## 発生した状況

1. CSMのUIで、セッションを `Curtain_leader` エージェントに紐づけた
2. セッション内で「あなたの役割を確認」と聞いた
3. Claudeは「親セッションとして動いている」「特定のエージェント定義に縛られていない」と回答
4. `.claude/agents/Curtain_leader.md` の内容を認識していなかった
5. ユーザーが「そうです（Curtain_leaderとして動くべき）」と教えて初めてエージェント定義を読みに行った

## 原因分析

CSMでセッションにエージェントを紐づけても、Claude Code本体に対して以下が伝わっていない:

- **このセッションがどのエージェントに紐づいているか**
- **エージェント定義ファイル（.md）の内容をセッション開始時に読み込むべきこと**

現状、`session-manager.json` の `agentSessions` にマッピング情報は保存されているが、Claude Code側のセッション開始時にそれを注入する仕組みがない。

## 期待される動作

1. CSMでセッションにエージェントを紐づける
2. そのセッションが開始（または再開）されたとき、紐づけられたエージェントの定義ファイルを自動で読み込む
3. Claudeが最初から自分の役割・配下エージェント・制約を認識した状態で応答する

## 提案する解決策

### 案1: SessionStart フックでエージェント定義を注入

セッション開始時のフック（`SessionStart` または `startup`）で:

1. `session-manager.json` の `agentSessions` から現在のセッションIDに対応するエージェント名を取得
2. そのエージェントの定義ファイル（`.claude/agents/<name>.md` または `.claude/agents/<name>/<name>.md`）を読み込む
3. セッションの初期コンテキスト（system-reminder等）にエージェント定義の内容を注入する

```
フロー:
SessionStart → セッションID取得 → agentSessions照合 → エージェント名特定
→ エージェント定義ファイル読み込み → コンテキストに注入
```

### 案2: セッション再開時にプロンプトを自動送信

セッション再開時に、CSMが自動的に以下のようなプロンプトを送信する:

```
あなたは {エージェント名} です。以下のエージェント定義に従って動作してください:
{エージェント定義ファイルの内容}
```

### 案3: CLAUDE.md または .claude/settings.json への動的書き込み

セッション切り替え時に、プロジェクトの `CLAUDE.md` やsettingsに現在のエージェント情報を一時的に書き込む。ただし複数セッション同時利用時に競合する可能性あり。

## 補足: 現在のsession-manager.jsonのマッピング例

```json
"agentSessions": {
    "Curtain_leader": {
        "sessionId": "ec3669a1-5774-4b07-a9d8-01bef5edd0fe",
        "sessionMode": "fixed"
    },
    "frevo-sv-master": {
        "sessionId": "",
        "sessionMode": "fixed"
    }
}
```

このマッピングは存在するが、Claude Code本体がこれを参照する仕組みがない。

## 優先度

**高** — エージェント機能の根幹に関わる問題。紐づけても認識されないなら、紐づけの意味がない。

# 追加要望: エージェント自身がCSMにフィードバックする仕組み

## 背景

エージェントが作業中に「CSMのこの仕組み、おかしいぞ」「期待通り動かない」「使いにくい」と気づくことがある。
例:
- 今回のagent-rules問題（パスがハードコードされている）
- エージェント役割が紐づけ後も認識されない
- セッション再開時の挙動が分かりにくい
- 配下エージェント情報が見つけにくい

しかし現状、エージェントはこれを記録する手段がなく、ユーザーが言語化して伝える必要がある。
**エージェントが気づいた瞬間に自動でCSMへフィードバックを送れるべき。**

## 提案

エージェントが「ここ変だ」と感じたら自分でフィードバックを生成できる仕組みを組み込む。

### 仕組み

**1. スラッシュコマンドまたはツール**

```
/csm-feedback bug "agentSessionsの紐づけ後もエージェント定義が読み込まれない"
```

または専用のツール（MCPツール等）として:

```
csm_report_issue({
    category: "bug",
    title: "...",
    description: "...",
    severity: "high"
})
```

**2. エージェント定義に「気づいたらフィードバックする」を組み込む**

エージェントの初期プロンプト（CSMが各エージェントに渡すシステムプロンプト）に以下を含める:

```
## CSMフィードバックルール

CSMの動作・UI・エージェント管理の仕組みについて
「おかしい」「期待と違う」「使いにくい」と感じたら、
すぐに /csm-feedback コマンドで報告すること。

報告すべき例:
- ドキュメントと実際の挙動が違う
- 紐づけたはずの設定が反映されない
- ファイルが期待と違う場所に作られる
- エラーメッセージが分かりにくい
- 機能が見つからない

報告しなくていい例:
- ユーザー固有のプロジェクトに関する問題
- 単純な使い方の質問
```

**3. 自動でメタデータを付与**

エージェントがフィードバックを送ると、CSMが自動で:
- セッションID
- エージェント名
- そのフィードバックに至った直前の操作（ツール呼び出し履歴）
- 該当ファイルパス（あれば）
- タイムスタンプ

を付与して `feedback/` フォルダに保存。

**4. ダッシュボードで一覧表示**

CSMサイドバーに「エージェントフィードバック」タブを追加。
- 未対応 / 対応中 / 完了
- カテゴリ（バグ / 要望 / 改善）
- 優先度
- どのエージェントが報告したか

### 期待される効果

- **改善ループが自動で回る**: エージェントが使っていて気づいた問題が即座に集約される
- **ユーザー負担が減る**: 「これ伝えて」と都度言わなくて済む
- **網羅性**: 一人のユーザーが気づかない問題もエージェントが拾える
- **再現性**: メタデータが自動付与されるので開発側で再現しやすい

### 実装イメージ

**a. 最小実装** — スラッシュコマンドだけ
```
/csm-feedback <category> <title>
→ docs/feedback/YYYY-MM-DD-<sessionId>-<title>.md を生成
```

**b. フル実装** — UIダッシュボード + エージェント定義への組み込み + メタデータ自動付与

## 優先度

**高** — エージェント主導の改善サイクルが回り始める鍵となる機能。
特にCSMはClaude+エージェントのために作られているので、
エージェント自身がフィードバックできる仕組みは本質的に重要。

### 理想形: 拡張機能のフィードバック窓口に直接送信

**最も嬉しい形**は、エージェントのフィードバックがCSM拡張機能の
公式フィードバック窓口（GitHub Issues / VS Code Marketplace のレビュー欄等）に
自動で投稿されること。

例:

```
/csm-feedback bug "..."
↓
CSM拡張がGitHub APIを叩いて Issue を自動作成
↓
リポジトリ: ratorin/claude-session-manager
タイトル: [Agent Feedback] エージェント定義が読み込まれない
本文: メタデータ込みで自動生成
ラベル: agent-feedback, bug, auto-reported
```

#### 実装案

**a. GitHub Issues 連携（推奨）**
- CSM拡張に GitHub Personal Access Token を設定
- `/csm-feedback` 実行時に GitHub REST API (`POST /repos/.../issues`) でIssue作成
- ラベル `agent-feedback` で自動分類
- 重複チェック（同じタイトルの未解決Issueがあればコメント追加）

**b. ローカル蓄積 + 一括送信**
- まず `feedback/` フォルダに保存
- ユーザーが「送信」ボタンで一括 GitHub Issues 化
- 内容を確認してから送れるので安心

**c. 設定で送信先を選択**
```json
{
    "claudeManager.feedback.target": "github",
    "claudeManager.feedback.repo": "ratorin/claude-session-manager",
    "claudeManager.feedback.token": "ghp_..."
}
```

#### メリット

- フィードバックが**開発者の目に確実に届く**
- GitHubの既存ワークフロー（Issue → PR → Close）に乗る
- 他のユーザーも同じ問題に気づける（公開Issue）
- バージョン情報・環境情報も自動添付できる

#### 補足

ユーザーが個人的なフィードバックを公開したくない場合のために、
「Private Issue」または「ローカル保存のみ」のオプションも用意すべき。
